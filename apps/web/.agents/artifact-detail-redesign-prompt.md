# Design Brief: Aqsha Artifact Detail Page

## The ask

Redesign the **Artifact Detail page** of Aqsha. It should be beautiful, calm, and a pleasure to use. The page is **highly dynamic** — it renders differently depending on the *type* of artifact being opened.

**You own the visual design.** Brainstorm the layout, hierarchy, and the best way to present each artifact type and its data — explore a few directions if it helps. This brief deliberately does **not** dictate grids, spacing, or component placement. It gives you two things only:

1. **The raw material** — what an artifact is, the types that exist, and the data each one carries. This is *what* must be displayable; *how* is yours to decide.
2. **Guardrails for fit** — our design tokens, fonts, and existing components, so your design stays on-brand and can drop straight into the app (Next.js + Tailwind + our component library).

Everything else — composition, emphasis, how a PDF vs. a diagram vs. a document should feel — is for you to design.

---

## Product context

Aqsha is a **playful, modern, minimalist AI writing & research workspace for students**. Brand essence: **"Ideas, neatly linked."** The mood is bright, airy, paper-like, and friendly — warm off-white paper in light mode, charcoal in dark mode. Voice is calm and clear, never fearful or jargon-y.

An **artifact** is any piece of content saved into a research workspace: an uploaded PDF or Word doc, a rich-text document the user writes, an AI-generated diagram or table, a saved web link, source code, and more. The Artifact Detail page is where someone opens a single artifact to **read, inspect, edit, or act on it**.

---

## What lives on this page — the content to display

There are **11 artifact types** (grouped loosely into 6 families). The page must gracefully present any of them. Here's what each is and the data it carries — treat this as the material to work with, not a layout instruction.

| Type | What it is | Content / data it has |
|---|---|---|
| **markdown** | A rich-text document the user writes & edits in-app (live editor, autosaves) | Editable body; autosave status (idle / saving / saved / failed) |
| **plain_text** | Plain text | Raw text |
| **code** | A code snippet/file | Source code, language, line count, byte size |
| **pdf** | An uploaded PDF (may be a scholarly paper — see below) | The document itself, file name, type, size; indexing status |
| **docx** | An uploaded Word document | File name, type, size, download |
| **html** | An HTML snippet/page | Rendered preview + raw source |
| **svg** | A vector image | Rendered image + raw source |
| **mermaid** | A diagram (flowchart, sequence, etc.) | Rendered diagram + diagram source |
| **json** | Structured data | Parsed structure + raw JSON |
| **csv** | Tabular data | Parsed table + raw CSV |
| **url** | A saved web link with extracted readable content | Extracted article text, site name, title, description, the link |

**Data present on every artifact:** title, type, source (how it arrived: manually created / uploaded / generated by the AI agent / saved from a URL), language, file name & size where relevant, a short text preview, created & updated times, and **indexing status** (whether it's been added to the workspace's searchable knowledge base).

**Scholarly papers (a PDF subtype).** When an uploaded PDF is detected as a research paper, it additionally carries parsed **bibliographic metadata**: paper title, authors (with affiliations), journal/venue, publisher, year, DOI, abstract, keywords, a confidence score (may be absent), and where the metadata came from. There's a separate parsing status for this (idle / parsing / ready / failed).

**Two status dimensions exist and can both be in flight** — surface them clearly however you see fit:
- **Indexing** (every artifact): not indexed / indexing / ready / failed.
- **Extraction** (only some types): URL link extraction, and scholarly-paper parsing — each pending / running / ready / failed.

**Actions the page supports today:** rename, download, open original (file or live URL), retry a failed extraction, move to another folder, delete. The user can also edit markdown documents inline.

## Layout we like — inspiration, not a spec

We're fond of the feel of our existing **Explore** and **Explore Detail** pages and would love this page to share that family resemblance — but **you decide the actual structure.** What we like about them:

- Editorial and content-centric: a comfortable, centered reading area, lots of calm whitespace.
- Flat surfaces with hairline dividers rather than heavy nested cards.
- A light metadata sidebar for properties, with the main content leading.
- A thin breadcrumb header at the top.
- Simple, understated text-style tab switching rather than chunky controls.
- Restrained type sizes, secondary info in muted tones, hierarchy from weight and spacing.

Take this as a *mood reference*. Feel free to depart from it where a given artifact type calls for something better.

## Design system — build within this (so it drops into the app)

Use our real tokens and fonts so the result is genuinely plug-and-play. Reference these by their semantic names (`bg-background`, `text-foreground`, etc.); don't invent new colors, fonts, or radii.

**Color — light:** warm-paper background `oklch(0.9195 0.0169 88.0030)`, near-black ink `oklch(0.2350 0 0)`, raised-paper card `oklch(0.9530 0.0156 86.4257)`, muted `oklch(0.8340 0.0232 87.1630)` / muted-foreground `oklch(0.4688 0.0136 84.5932)`, border `oklch(0.8434 0.0231 87.1621)`, destructive (red) `oklch(0.5771 0.2152 27.3250)`.
**Color — dark:** charcoal background `oklch(0.1913 0 0)`, warm-mist text `oklch(0.9173 0.0133 82.4015)`, card `oklch(0.2264 0 0)`, muted `oklch(0.2850 0 0)`, border `oklch(0.2931 0 0)`.

> **Primary is a neutral dark charcoal, not a bright blue.** Keep it neutral.

**Accent palette (soft, friendly chips):** sky (used for links), mint (success / "ready"), lemon, lavender, coral. Each has a soft background + foreground variant in both modes. Natural fit for color-coding status (e.g. ready → mint, in-progress → lemon, failed → red, idle → muted) — use sparingly and consistently.

**Fonts (actually loaded):** **Inter** for body & UI, **Playfair Display** for display headings (`.font-heading`), **JetBrains Mono** for code / data / source. Hierarchy comes from weight, scale, and color — not letter-spacing.

**Shape & feel:** base radius 8px (cards ~12px, badges are full pills), generous 4px-based spacing, mostly flat surfaces. There's one signature soft-paper shadow with a subtle top-edge highlight — reserve it for hero/elevated surfaces; keep most things flat.

**Icons:** all from `@aqsha/ui/icons` (Hugeicons-backed, Lucide-compatible names). No raw `lucide-react`.

## Existing building blocks (so your design is buildable)

You don't need to invent viewers — these already exist and can be styled into your design:

- **Markdown** → in-app rich-text editor (BlockNote) with autosave.
- **PDF** → embedded, theme-aware document viewer; scholarly papers add a parsed-metadata panel.
- **Mermaid** → rendered diagram.
- **HTML / SVG** → sandboxed live preview.
- **JSON** → structured key/value viewer. **CSV** → table viewer. (Both show a bounded preview of large data.)
- **Code / plain text** → readable prose / source view with copy.
- **URL** → reader view of the extracted article.

Component library available: buttons, badges, cards, tabs, inputs, tooltips, skeletons, dialogs, dropdowns, popovers, sheets, separators, scroll areas, and the app shell with its left sidebar. Source/raw views use a mono code block with a copy button.

## States to cover

Design these (they're frequent and currently underwhelming):
- **Loading** — placeholders that hint at the final shape.
- **Content failed to load** — calm message + retry.
- **Empty / not found / wrong workspace** — a friendly dead-end with a way back.
- **Processing** — indexing in progress, scholarly-paper parsing in progress, and URL extraction pending/failed (with retry). Show progress without alarming the user.
- **Markdown autosave** — quiet idle / saving / saved / failed feedback.

**Microcopy:** friendly, clear, calm, single-language **English**. (Today it's a mix of English and Indonesian — please unify to English.) Lead with clarity, never fear or "AI magic" language.

## Not built yet — don't assume these exist

These don't exist in the product today. You may *propose* them as optional/future ideas, but the page must be complete and shippable without any of them — and please label them clearly as net-new so they aren't mistaken for existing behavior:

- A **chat side panel** to talk about the open artifact (current chat is thread-scoped, not artifact-scoped).
- **Version history** UI (versions are stored but not exposed to this page).
- **Citation export** (BibTeX / formatted citations) for scholarly papers.

---

## Light & dark

Design both modes (light = warm paper / charcoal ink; dark = charcoal / warm-mist text), via our standard theme toggle. Make sure status colors, accents, and links stay legible in both.

---

## Deliverable

High-fidelity mockups in **light and dark** that show how the page handles its different artifact types (the **scholarly PDF** and the **markdown editor** are the highest-value, most layout-distinct cases — good ones to lead with) plus the key states above.

**Show us your thinking on layout and hierarchy** — a direction or two is welcome. The visual design, structure, and how best to present each feature are yours to decide; we'll bring it on-brand from there using the tokens and components above.
