Bagaimana Sistem Memproses Upload PDF Paper
di Halaman Workspace Detail

Visualisasi step-by-step dari momen user memilih file PDF, sampai paper ter-enrich penuh dan siap di-query untuk RAG / konteks workspace. Mencakup jalur client → Convex storage → ekstraksi teks → indexing RAG, lalu 2 jalur enrichment paralel & terpisah: resolusi metadata berbasis identifier (DOI/arXiv → Crossref/OpenAlex) + fallback LLM, dan ekstraksi struktural GROBID.

Route: /app/workspaces/[workspaceId]  ·  Stack: Next.js 16 (apps/web) + Convex (packages/convex)  ·  Lompat ke: Tabel status · Peta file

Diperbarui 2026-06-09 untuk pipeline enrichment baru: GROBID + resolver di-decouple dari sukses ekstraksi teks, resolver identifier + fallback LLM ditambahkan, dan gate metadata di UI dilonggarkan.

01 User memilih file di workspace detail

Interaksi UI murni. File belum menyentuh server — hanya divalidasi & dimasukkan ke antrian upload.

ClientUser trigger upload (klik atau drag-drop)

Dua entry point: menu konteks “Upload file” yang menembak fileInputRef.current?.click(), atau drag-drop zone di area library (onDragEnter/Over/Leave/Drop). Keduanya memanggil uploadToActiveFolder(files). Input menerima multiple file dengan accept={WORKSPACE_UPLOAD_ACCEPT}.

Untuk tiap file, uploadWorkspaceFile() menjalankan tiga panggilan backend berurutan. File mentah masuk storage dulu, baru dibuat record-nya.

Convex FnA · Minta upload URL

Client memanggil mutation api.artifacts.generateUploadUrl (via useConvexMutationFn). Backend memverifikasi user adalah owner workspace, lalu mengembalikan ctx.storage.generateUploadUrl().

03 Server-side: buat record + ekstraksi teks + indexing RAG

createFromStorage (Node runtime) memvalidasi ulang, menyisipkan record DB, lalu memanggil finalizeUploadedDocument() yang mengurus ekstraksi teks dan vektorisasi.

Convex FnValidasi ulang + insert record artifact

Server validateUpload() lagi (nama, size, tipe didukung), menentukan artifactType (pdf/docx/…) dari nama+mime, lalu internal mutation createUploadedArtifactInternal menyisipkan: baris artifacts dengan source: "upload" + indexingStatus: pending, dan baris artifactContents kosong.

artifactUploads.ts:59–80 artifacts.ts:884–939
Convex FnEkstraksi teks dari PDF

extractStoredDocument() mengambil blob dari storage. Untuk PDF dipakai library unpdf: getDocumentProxy() + extractText(pdf, {mergePages:true}). (DOCX → mammoth; teks/markdown/csv → UTF-8 langsung.) Hasil dinormalisasi (hapus null, rapikan whitespace). Jika tak ada teks terbaca → indexing failed — tapi kini ini tidak lagi membatalkan jalur enrichment (Fase 04 tetap jalan, lihat note di bawah). 

const { extractText, getDocumentProxy } = await import("unpdf");
const pdf = await getDocumentProxy(new Uint8Array(buffer));
const { text } = await extractText(pdf, { mergePages: true });

patchUploadedArtifactIndexed menyimpan markdown + plainText (atau storageId-nya), ragEntryId, indexedAt, dan mengubah status menjadi indexingStatus: ready. Pada titik ini paper sudah searchable lewat RAG meskipun enrichment belum jalan.

Return ke client + enrichment di-decouple. createFromStorage mengembalikan { artifactId, title, indexed } → toast complete. Lalu, untuk PDF ber-workspaceId, queuePaperEnrichment() menjadwalkan 2 jalur enrichment paralel (Fase 04) secara asinkron. 04 Enrichment metadata: 2 jalur paralel & terpisah

Untuk PDF ber-scope workspace, queuePaperEnrichment menjadwalkan dua jalur independen yang berlomba mengisi artifactPaperMetadata: (4a) resolusi metadata berbasis identifier + fallback LLM, dan (4b) ekstraksi struktural GROBID. Keduanya idempoten dan digabung lewat aturan rank (lihat note merge). Filosofi baru: metadata paling konsisten datang dari resolusi identifier ke database, bukan dari parsing PDF yang rapuh.

4a · Resolusi identifier-first + fallback LLM — jalur baru, butuh teks

Convex FnCari DOI / arXiv di region header

classifyPaperText() mengekstrak identifier hanya dari region header paper — potongan teks sebelum heading “References/Bibliography”, di-cap ≤ 3.000 char (paperHeaderRegion). Ini mencegah DOI dari daftar pustaka (paper yang dikutip) salah dipakai sebagai identitas paper ini. arXiv dicek sebelum DOI (mengikuti precedence classifyUrl).

paperIngest/uploadIdentifiers.ts · classifyPaperText:43, paperHeaderRegion:26
ExternalResolve metadata otoritatif

Jika ada identifier → resolvePaper() (di-reuse dari jalur URL) me-resolve dari Crossref / OpenAlex / arXiv / DataCite / Semantic Scholar dengan cache provider. Hasil bersih (judul/penulis/abstrak/DOI/jurnal/tahun) — tidak pernah “salah baca abstrak”. Tidak menyentuh rate-limit paperIngestPerUser (itu hanya di wrapper ingestUrl).

paperMetadataEnrichment.ts · enrichUploadedPaperMetadata:78 paperIngest/resolve.ts:22
ExternalFallback LLM (structured output)

Tidak ada identifier? → fallback generateObject (AI SDK, model CHAT_LITE_MODEL ≈ gpt-5.4-mini) atas teks halaman pertama, dengan schema Zod (title/authors/abstract/doi/journal/year + flag isResearchPaper). Env-gated via isLlmMetadataEnabled() (LLM_METADATA_ENABLED, default on bila chat key terpasang).

paperMetadataEnrichment.ts · isLlmMetadataEnabled:34
Convex FnTulis metadata + tandai scholarly

upsertResolvedPaperMetadata menulis artifactPaperMetadata dengan metadataSource = crossref/openalex/arxiv/datacite/semantic_scholar atau llm, plus confidence (resolver 0.95, LLM 0.4). Lalu setArtifactDetectedKind menandai detectedDocumentKind: "scholarly_paper" — jadi metadata tampil walau GROBID gagal/mati.

paperExtractions.ts · upsertResolvedPaperMetadata:248, setArtifactDetectedKind:342

4b · Ekstraksi struktural GROBID — baca byte PDF langsung, jalan walau teks kosong

Convex FnAntrikan + jalankan GROBID

queueGrobidExtraction membuat baris artifactExtractions (extractor: "grobid", pending, attemptId dedup) lalu runGrobidExtraction POST ke ${GROBID_BASE_URL}/api/processFulltextDocument (consolidate header/citations, timeout 90s) → running → TEI XML.

paperExtractions.ts · queueGrobidExtraction:372, runGrobidExtraction:436 paperExtraction/grobidClient.ts:14
Convex FnParse TEI → simpan + tandai siap

parseGrobidTei() mengekstrak judul/abstrak/DOI/penulis/afiliasi/jurnal/tahun/keywords/seksi/referensi + confidence. TEI/sections/references disimpan sebagai blob, plain-text di-index ulang ke RAG (lebih bersih dari unpdf). markGrobidReady meng-upsert artifactPaperMetadata (metadataSource: "grobid") + artifactExtractions → ready.

Merge & rank (anti-clobber). METADATA_SOURCE_RANK: manual(4) > grobid(3) > resolver(2) > llm(1). Sumber yang lebih lemah tidak pernah menimpa yang lebih kuat, dan db.patch hanya menulis field yang benar-benar ada (tidak meng-clobber pdfStatus/sourceUrl/keywords dari pass sebelumnya). markGrobidReady juga tidak pernah menurunkan scholarly_paper → generic. paperExtractions.ts · METADATA_SOURCE_RANK + upsertResolvedPaperMetadata:248, isLikelyScholarlyPaper:781
Retry & degradasi anggun. GROBID: error transien (50x / timeout) di-retry hingga 3×, lalu markGrobidFailed (failed). LLM/resolver: error ditangkap, best-effort. Paper tetap searchable via teks dasar Fase 03; metadata kini punya 2 sumber independen, jadi kegagalan satu jalur tidak lagi berarti “tanpa metadata”. paperExtractions.ts · markGrobidFailed:676
05 Hasil akhir: paper siap di-query

Data tersebar di vector store + beberapa tabel. Frontend memantau via polling, dengan gate metadata yang sudah dilonggarkan.

Convex FnFrontend polling status

UI memanggil query paperExtractions.getStatus({ artifactId }) → { extraction, metadata }. extraction.status berasal dari baris GROBID; metadata dari artifactPaperMetadata (sumber GROBID atau resolver/LLM).

derivePaperMetadataView() kini menampilkan metadata kapan pun “usable” (ada title/abstract/authors) — tidak lagi mensyaratkan detectedDocumentKind === "scholarly_paper" (perbaikan akar masalah “metadata tidak terlihat”). Tambah state pending (“Reading paper details…”, SidebarPending); banner failed tidak alarm bila metadata sudah ada.

RAG storeApa yang queryable

Vektor di artifactRag (namespace user:{id}, filter artifactId + workspaceId) untuk pencarian semantik; artifactPaperMetadata untuk UX paper; artifactContents untuk teks/markdown lengkap.

Tahu keterbatasanFollow-up tertunda

UI pending/failed & tombol retry masih terikat ke baris GROBID saja — retry belum men-trigger ulang resolver/LLM, dan tak ada spinner saat GROBID dimatikan. Butuh sinyal “enrichment status” tersendiri (keputusan skema, ditunda).

Cabang alternatif — paper dari URL (bukan upload manual). Jika user menambah URL (DOI/arXiv/PMID), createUrl → ingestUrl mengklasifikasi URL, me-resolve metadata dari CrossRef / OpenAlex / arXiv / DataCite / Unpaywall / Semantic Scholar, mengunduh PDF open-access bila ada, lalu convertUrlArtifactToPdf + finalizeStoredArtifact menjalankan pipeline Fase 03–04 yang sama. Jika tak ada PDF, metadata disimpan saja (metadata-only). paperIngest/ingest.ts:31–124 paperIngest/resolve.ts
