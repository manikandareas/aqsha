00

Ringkasan Eksekutif

Tiga kesimpulan utama dari evaluasi, yang menjadi dasar seluruh rancangan di bawah.

1 · Fondasinya sehat — jangan ganti, perkuat.

Arsitektur saat ini (dua agen Astra di atas satu store components.agent, tool diinjeksi per-call, HITL native via tool parts, deep research sebagai durable workflow, schema sidecar yang dipartisi ownerUserId) adalah pola yang benar untuk Convex. Sudah ada benih verifikasi yang serius: citationChecks, auditClaims dua-tahap, scoring kualitas+reliabilitas dua-poros, dan gate kesiapan bukti deterministik. Rancangan ini tidak mengganti arsitektur — ia menambah tiga lapisan dan memperbaiki 21 titik rapuh.

2 · Ada hutang teknis yang akan meledak saat kapabilitas bertambah.

Empat temuan kritis (gating executeArtifact yang bergantung pada satu mekanisme implisit, billing yang diturunkan dari string model, deteksi sukses deep-research via pencocokan string, dan kredit yang dikonsumsi sebelum cek cache) semuanya jenis bug yang diam-diam salah — bukan crash. Begitu lapisan sandbox dan multi-agent menambah jumlah jalur eksekusi, biaya memperbaikinya berlipat. Fase 0 roadmap adalah melunasi hutang ini dulu.

3 · Tren 2026 menunjuk persis ke arah positioning Aqsha.

Mayoritas tren mendorong agen menghasilkan lebih banyak — dan memperburuk krisis integritas (sitasi fabrikasi di NeurIPS 2025, peer review tanpa verifikasi sitasi sistematis). Kebutuhan yang meledak justru verifikasi. Astra sudah punya 60% bahan bakunya. Yang ditambahkan rancangan ini: (a) sandbox Daytona sebagai instrumen komputasi (statcheck, GRIM/GRIMMER, power analysis, replikasi, metafor), (b) verifikasi sitasi 4-langkah, (c) orkestrasi multi-agent di deep research, (d) Agent Skills (standar terbuka agentskills.io) sebagai lapisan pengetahuan prosedural yang membuat agen berjalan otonom per-domain tanpa hardcode prompt, (e) ekspos sandbox sebagai MCP server agar interoperable.

02

Temuan Audit Berperingkat

21 temuan terpenting dari ~109 gotcha yang terdokumentasi, ditambah analisis lintas-subsistem. Setiap temuan memuat rekomendasi perbaikan konkret. Format ID: AUD-xx, dirujuk kembali oleh roadmap.

Kritis — perbaiki sebelum menambah kapabilitas apa pun

AUD-01
Kritis

Gating executeArtifact bergantung pada satu mekanisme implisit (activeTools)

executeArtifact tidak punya needsApproval; satu-satunya penghalang tulis-tanpa-persetujuan adalah daftar activeTools di runInlineGeneration. Komentar kode malah menyebut prepareStep yang tidak pernah ada — call site baru (mis. jalur sandbox/multi-agent baru) yang lupa meneruskan activeTools akan membuka tulis artifact satu-tembakan tanpa propose yang disetujui.

Perbaikan: defense-in-depth — di dalam executeArtifact.execute, validasi server-side bahwa ada proposeArtifact ber-status approved pada step sebelumnya di thread yang sama (atau token approval yang dipersist saat approve). activeTools tetap dipakai sebagai UX-gate, tapi bukan satu-satunya gate. Hapus/koreksi komentar prepareStep.
AUD-02
Kritis

Fitur billing diturunkan dari string model, bukan dari konteks run

recordUsage menentukan pro_chat vs normal_chat dengan model === CHAT_PRO_MODEL. Jika env lite dan pro pernah diset ke model yang sama (sangat mungkin saat eksperimen model), seluruh penggunaan pro tertagih sebagai normal — tanpa error apa pun. Usage handler memang tidak menerima agentKind, tapi itu pilihan yang bisa diubah.

Perbaikan: teruskan agentKind (dan kelak feature eksplisit seperti sandbox_compute) melalui closure usageHandler per-call — handler sudah dibuat per call di runInlineGeneration, jadi tinggal menangkap variabel. String model hanya untuk atribusi, bukan keputusan billing.
AUD-03
Kritis

Deteksi sukses deep-research via pencocokan string output tool

Cabang deep di runInlineGeneration memindai hasil tool untuk output.status === "deep_research_started". Jika bentuk return startDeepResearch berubah, workflow tetap mulai sementara messages.ts menandai run selesai dan melepas composer — double-completion yang sukar didiagnosis.

Perbaikan: ekstrak konstanta + tipe return bersama (DeepResearchStartedResult) di satu modul yang diimpor kedua sisi; tambahkan type guard, dan unit test kontrak yang gagal saat bentuknya berubah. Pola sama dipakai untuk hasil tool sandbox (SandboxRunResult).
AUD-04
Kritis

Kredit & token rate-limit dikonsumsi sebelum cek cache provider

limitExternal berjalan di awal fungsi, sebelum readCachedCandidates — cache hit tetap menagih kredit dan membakar bucket 20/menit. Pada deep research yang memanggil puluhan lookup per ronde, ini menggandakan biaya pengguna dan bisa memblokir run pada data yang sebenarnya sudah ada.

Perbaikan: pindahkan urutan menjadi cache read → (miss) → gate → fetch → cache write. Bila metering per-permintaan memang diinginkan, pisahkan: rate-limit tetap di depan (murah), konsumsi kredit hanya pada cache miss, atau tagih tarif "cached" yang lebih rendah lewat estimateCredits.

Tinggi — sumber bug nyata atau penghambat rancangan baru

AUD-05
Tinggi

Citation counter tidak diinjeksi pada normal chat — nomor sitasi bisa tabrakan dalam satu giliran

requireCitationCounter selalu jatuh ke counter baru per tool call, sehingga dua panggilan searchWeb + searchArxiv sama-sama mulai dari [1]. Rekonsiliasi post-hoc di persistCited mendedup berdasarkan sourceKey, tapi marker [1] di teks model menjadi ambigu — menunjuk dua sumber berbeda.

Perbaikan: buat satu createCitationCounter() per giliran di runInlineGeneration dan injeksikan ke ctx semua tool riset (field citationCounter sudah ada di AqshaToolCtx — tinggal diisi). Nomor jadi unik se-giliran; persistCited tak perlu menebak.
AUD-06
Tinggi

Tiga daftar nama tool HITL disinkronkan manual (server, client, instruksi)

HITL_TOOL_NAMES di messages.ts, hitl-parts.ts di client, dan teks instruksi runtime harus identik. Drift diam-diam merusak deteksi pause atau gating — dan lapisan sandbox akan menambah tool ber-approval baru ke ketiganya.

Perbaikan: satu konstanta di package shared (@aqsha/convex sudah jadi dependensi web) yang diimpor server & client; instruksi runtime digenerate dari konstanta yang sama saat build instruksi.
AUD-07
Tinggi

Run ber-status waiting tidak dianggap aktif — send baru lolos saat HITL menggantung

hasActiveReplyRun hanya menghitung queued|running. Pengguna bisa mengirim pesan baru saat approval menggantung; resume kemudian berebut state dengan run baru. Ditambah scan hanya 8 run terakhir, run aktif bisa terlewat pada thread sibuk.

Perbaikan: sertakan waiting dalam definisi aktif (UI sudah memblokir composer via hitlBlocking, jadikan konsisten di server), atau definisikan kebijakan eksplisit "send baru = auto-deny pending HITL". Ganti scan take(8) dengan indeks by_owner_thread_status.
AUD-08
Tinggi

Jalur resume HITL tidak mendapat konteks RAG segar

RAG hanya dibangun saat prompt dan visiblePrompt tersedia; resumeGeneration tidak meneruskan keduanya, sehingga giliran setelah jawaban askUser kehilangan konteks dokumen — padahal jawaban pengguna sering kali justru menentukan dokumen mana yang relevan.

Perbaikan: pada resume, bangun query RAG dari jawaban HITL terakhir + pesan user terakhir (keduanya sudah ada di message store), lalu prepend seperti jalur normal.
AUD-09
Tinggi

Kandidat "Provider unavailable" bisa dikutip model sebagai sumber

Kegagalan provider dinormalisasi menjadi kandidat weak bertitel "Provider unavailable" dengan pesan error di locator/snippet. Untuk searchWeb ini memicu fallback Jina (bagus), tapi untuk arXiv/DOI kandidat sintetis itu masuk ke daftar yang model bisa kutip — pesan error bocor sebagai "sumber".

Perbaikan: saring kandidat providerFailureReason() sebelum numberCandidates di jalur tool; kembalikan ke model sebagai pesan status terstruktur ({ok:false, reason}), bukan sebagai kandidat. (Deep loop sudah menyaringnya — samakan perilaku.)
AUD-10
Tinggi

Verifikasi klaim memakai model lite, sekuensial, maksimal 16 klaim

Justru pada langkah yang menjadi nilai jual platform (audit klaim), semua panggilan LLM hardcode DEEP_LITE_MODEL dan berjalan satu-per-satu dalam for-loop. Run pro tidak benar-benar "pro" di tempat yang paling penting, dan latensi audit linear terhadap jumlah klaim.

Perbaikan: (a) verifikasi klaim memakai deepModelForAgent(agentKind) minimal untuk klasifikasi contradicted/unsupported; (b) batch paralel dengan Promise.all ber-konkurensi terbatas (rate limit aman karena ini panggilan LLM, bukan provider eksternal); (c) jadikan cap 16 konfigurable per-tier.
AUD-11
Tinggi

researchRuns adalah referensi tabel menggantung di union runId

v.id("researchRuns") dirujuk di banyak tabel padahal tabelnya tidak didefinisikan — validator yang tidak pernah bisa terpenuhi, membingungkan pembaca skema dan tooling.

Perbaikan: hapus dari union (migrasi aman: tidak ada baris yang mungkin memuatnya) atau definisikan tabelnya bila memang reserved. Sekalian konsolidasikan enum duplikat partially_supported|partial di citationChecks.support dengan normalisasi saat tulis.
AUD-12
Tinggi

Billing deep research flat & estimasi token len/4 — keduanya terlepas dari biaya nyata

Run deep ditagih flat 120/60 kredit berapapun ronde aktualnya; estimasi token len/4 dipakai untuk gate kredit dan cek globalTokenUsage (yang konsumsinya advisory). Saat sandbox menambah dimensi biaya (menit compute), model flat semakin tidak akurat.

Perbaikan: tetap flat di muka (UX yang baik), tapi tambahkan rekonsiliasi: catat biaya aktual (token + panggilan provider + menit sandbox) ke providerUsageLedger per run, dan kalibrasi tarif flat dari data rollup berkala. Estimasi token diganti tokenizer ringan (mis. heuristik per-bahasa atau tiktoken approx di mutation tidak bisa — cukup kalibrasi konstanta dari data ledger).

Sedang — perbaiki saat menyentuh modul terkait

AUD-13
Sedang

Hasil kosong di-cache 24 jam

Status empty dan ready sama-sama TTL 24h — kueri yang kebetulan nihil tidak dicoba ulang sehari penuh meski korpus berubah (arXiv terbit harian).

Perbaikan: TTL bertingkat: ready 24h, empty 1–2h, failed 10–15m.
AUD-14
Sedang

arXiv global 1 req/3s menjadi bottleneck lintas-user

Etiket arXiv benar dihormati, tapi bucket fixed-window global membuat burst dua pengguna saling memblokir dengan error "rate limited" alih-alih antre.

Perbaikan: antrekan, jangan tolak — bungkus panggilan arXiv dalam work queue kecil (komponen @convex-dev/workpool atau scheduler retry dengan backoff) sehingga pengguna mengalami latensi, bukan kegagalan. Prioritaskan OpenAlex/Crossref untuk metadata yang sama bila tersedia.
AUD-15
Sedang

Lantai kesiapan bukti tinggi → banyak run berakhir budget_exhausted/partial

Early-stop butuh ≥10 sumber readable, ≥8 extract, ≥4 domain, ≥3 bucket. Untuk topik sempit (lazim di riset akademik) lantai ini sulit dicapai dalam 2 ronde lite — run lite hampir selalu "partial".

Perbaikan: skala lantai terhadap tier dan terhadap sufficiencyCriteria rencana (mis. lite: 6/5/3/2). Tampilkan ke pengguna kenapa partial — lantai mana yang belum tercapai (datanya sudah ada di assessEvidenceReadiness).
AUD-16
Sedang

Dua sinyal blokir composer (run status vs hitlBlocking turunan client)

Saat pause HITL, thread sidecar tetap di-idle-kan dan blokir hanya dari derivasi part di client. Bila string state part berubah versi, composer bisa macet terbuka/tertutup tanpa jejak server.

Perbaikan: tambah status sidecar waiting_hitl yang diset bersama completeInlineRun(keepWaiting); client memakai OR dari kedua sinyal. Sekaligus menyelesaikan AUD-07 secara konsisten.
AUD-17
Sedang

Konteks prompt double-prepend tanpa anggaran gabungan

RAG (6k) + bodi dokumen (16k) + manifest bersifat aditif dan urutan finalnya (retrieved → document → "User message:") tidak pernah dievaluasi sebagai satu anggaran. Pada model context-window kecil, prompt bisa bengkak diam-diam; dan konten RAG bisa duplikat dengan bodi dokumen yang sama.

Perbaikan: satu context assembler dengan anggaran total (mis. 20k char), dedup chunk RAG terhadap artifact yang bodinya sudah disertakan penuh, dan label blok yang konsisten. Ini juga tempat menyuntikkan blok <computation_context> hasil sandbox nanti.
AUD-18
Sedang

Jalur error composer tidak merestorasi konten; startThread tanpa optimistic echo

Catch generik (error jaringan pasca-clear) menghilangkan teks yang diketik; pesan pertama thread baru tidak punya echo instan.

Perbaikan: panggil restoreComposerContentAfterBlockedSend juga di catch; untuk startThread, render echo lokal sementara sampai navigasi + subscription siap.
AUD-19
Sedang

Kapabilitas yang sudah dibayar tapi tidak dipakai

evidenceStrength dipersist tapi tak dirender; planResearch action paralel/legacy tak dipakai jalur live; reason duplicate di SourceQuality mati; approveTool.workspaceId diterima tapi tidak diinjeksikan ("Phase 2.3").

Perbaikan: render badge evidenceStrength di panel sumber (murah, menambah persepsi rigor); hapus planResearch & reason mati; selesaikan atau cabut parameter workspaceId.
AUD-20
Sedang

Pembatalan deep research hanya dicek di batas ronde

ensureNotCanceled dicek di awal ronde/step — cancel di tengah fan-out discovery/read panjang tidak menghentikan apa pun sampai checkpoint berikutnya (biaya terus berjalan).

Perbaikan: cek pembatalan juga sebelum setiap fan-out provider dan sebelum setiap batch read; sandbox runner wajib menerima sinyal cancel (hapus sandbox = stop biaya).
AUD-21
Sedang

Duplikasi kecil yang menumpuk

USER_AGENT/userAgent() duplikat verbatim di dua modul; mention markers harus mirror manual dengan context-refs.ts; sentinel "Thread baru" magic-string di 4 tempat.

Perbaikan: konsolidasikan ke modul konstanta bersama (shared/constants.ts) — sekali jalan bersama AUD-06.

Tesis strategis

Saat 40% aplikasi enterprise menyematkan agen (Gartner, akhir 2026), volume keluaran agen meledak — dan bersamanya volume klaim & sitasi yang tidak terverifikasi. Posisi Aqsha bukan "agen riset yang lebih cepat", melainkan agen riset yang keluarannya sudah tersaring kualitasnya: setiap laporan membawa bukti komputasi yang bisa direproduksi, sitasi yang tervalidasi 4 langkah, dan klaim yang teraudit. Itu produk yang tren 2026 ciptakan permintaannya, dan kompetitor generik tidak punya infrastrukturnya.

Tiga invariannya

  • Convex storage adalah source of truth; sandbox selalu ephemeral. File dihidrasi dari ctx.storage.get(storageId) saat task mulai, output dipersist balik via ctx.storage.store(blob) dan didaftarkan sebagai artifact, sandbox dihapus. Filesystem sandbox tidak pernah dianggap penyimpanan.

Angka hasil recompute disimpan apa adanya di computationChecks; interpretasinya ("konsisten/diskrepan") adalah field terpisah dengan aturan eksplisit. Sama seperti pemisahan sourceQuality vs domainReliability yang sudah ada.
  • Setiap kapabilitas baru lewat gerbang biaya yang sama: kredit plan → rate limit → eksekusi → ledger → rollup. Feature enum bertambah (sandbox_compute, citation_verify), mekanismenya tidak.

Lapisan Sandbox (Daytona)

Sandbox bukan fitur "code execution" — ia instrumen integritas riset. Framing ini menentukan semua keputusan di bawah: image apa yang dibangun, tool apa yang diekspos ke model, dan kapan sandbox boleh menyala.

Pola integrasi tiga-file (constraint runtime Convex)

SDK TypeScript Daytona membutuhkan API Node (Buffer, streaming) yang tidak tersedia di V8 isolate default Convex. Solusinya — yang juga sudah dipakai ragContext.ts — adalah isolasi total di Node action:

Deep Research sebagai Pipeline Multi-Agent

Prinsip: subagen = workflow step ber-kontrak, bukan framework baru. Tantangan multi-agent 2026 yang belum selesai adalah koordinasi — Convex Workflow yang sudah terpasang justru menyelesaikan koordinasi secara durable (checkpoint, retry, onComplete). Yang perlu dilakukan adalah dekomposisi, bukan adopsi orkestrator eksternal.

Dari monolit ke pipeline

Saat ini researchLoop (~3.2k LOC modul) menjalankan semua peran dalam satu action. Dekomposisi target — setiap subagen adalah internalAction dengan kontrak input/output tertipe (gaya Agent Card: nama, kapabilitas, skema tugas), dipanggil sebagai step.runAction:

deepResearchExecuteWorkflow v2 — step berlabel; ⇄ = paralel (maxParallelism 6 sudah menampung)
1 · literatureAgent (per ronde)discover → rerank → validateAndRead → assess — kode eksisting diekstrak apa adanya; kontrak keluar: AcceptedSource[] + extracts
2 · counterEvidenceAgenteksisting, kini step terpisah agar bisa retry sendiri
3a ⇄ statisticalAgentdeteksi klaim kuantitatif pada sumber accepted + paper konteks → sandbox recompute → computationChecks. Paper kuantitatif: default jalan, ekstrak angka utama + cek integritas ringan
3b ⇄ citationAgentverifikasi 4-langkah semua sumber final → integrityStatus. Paralel dengan 3a — keduanya hanya butuh keluaran step 1–2
4 · writerAgentsynthesize dengan konteks tambahan: computationChecks + integrityStatus → laporan yang sudah tersaring kualitasnya, bukan ringkasan
5 · auditorAgentklaim span-level (Modul 3) → revisi → verificationReport

Aturan koordinasi (yang membuat ini tetap sederhana)

  • Komunikasi hanya lewat data ber-skema di Convex (researchSources, computationChecks, dst.) — tidak ada message-passing antar agen. Workflow step membaca keluaran step sebelumnya dari argumen/DB; debugging = membaca tabel.
  • Kegagalan subagen verifikasi tidak menggagalkan run. 3a/3b memakai ACTION_RETRY yang sama; bila tetap gagal, laporan terbit dengan bagian "Verifikasi tidak lengkap" eksplisit — degradasi yang jujur, konsisten dengan filosofi Evidence Limits yang sudah ada.
  • Anggaran per-subagen, bukan hanya per-run: budgetJson di agentRuns diperluas menjadi alokasi per step (token, panggilan provider, menit sandbox) — pelacakan biaya multi-agent yang jelas, dan dasar rekonsiliasi billing AUD-12.
  • Observabilitas memakai jalur eksisting: setiap subagen menulis agentRunEvents dengan stepKey miliknya (eventType baru: compute, citation_check) — progress panel UI langsung menampilkan aktivitas verifikasi tanpa plumbing baru.
  • Setiap subagen membawa skill-nya sendiri (delegasi subagen, §08). Subagen literatur mengaktifkan deep-research-guide + paket domain yang cocok; statistik memuat stat-verification; penulis memuat skill gaya sitasi/bahasa. Instruksi domain tidak membengkakkan konteks subagen lain — dan mengganti metodologi = mengganti skill, bukan kode.
  • Chat inline tidak menjadi multi-agent. Lite/pro tetap satu agen + tool; orkestrasi multi-agen hanya pada workflow durable, tempat ia benar-benar terbayar.

Kesiapan A2A tanpa adopsi A2A

Karena tiap subagen sudah berbentuk (kapabilitas + skema tugas + kontrak hasil), memetakannya ke Agent Card A2A v1.0 kelak adalah pekerjaan adaptor, bukan refactor. Pemicu adopsi yang disepakati: saat ada kebutuhan nyata berkolaborasi dengan agen eksternal (mis. agen institusi/penerbit) — bukan sebelum itu.

Lapisan Agent Skills — Pengetahuan Prosedural yang Bisa Dipasang

Agent Skills (agentskills.io) adalah standar terbuka: sebuah skill = folder berisi SKILL.md (frontmatter name + description + instruksi Markdown) plus opsional scripts/, references/, assets/. Mengapa ini menutup gap otonomi terbesar Astra

Saat ini seluruh pengetahuan prosedural Astra terkunci di kode: SHARED_INSTRUCTIONS di runtime.ts, buildPrompt 10 slash command, prompt internal deep research (bucket planning, sufficiency, sintesis) tersebar di deepResearch.ts. Dan karena formatnya standar terbuka, Aqsha bisa mengimpor ekosistem skill komunitas yang tumbuh — sekaligus skill buatan Aqsha portabel ke Claude Code/Codex/Gemini CLI, saluran distribusi gratis menuju peneliti.

Interoperabilitas: Sandbox & Verifikasi sebagai MCP Server

MCP kini standar de-facto (Linux Foundation, 97jt+ unduhan, didukung semua lab besar). Mengekspos kapabilitas verifikasi Aqsha lewat MCP membuatnya dapat dipakai agen internal mana pun dan menjadi titik integrasi terbuka — peneliti bisa memanggil verifikasi Aqsha dari Claude/IDE/agen mereka sendiri.

Implementasi di Convex

  • Transport: MCP Streamable HTTP di atas Convex HTTP actions (convex/http.ts) — tidak butuh server terpisah. Endpoint /mcp menerima JSON-RPC, mendelegasikan ke action/mutation internal yang sama dengan yang dipakai tool agen (satu implementasi, dua permukaan).
  • Auth: API key per-user (tabel apiKeys baru) yang dipetakan ke ownerUserId — seluruh gerbang kredit/rate-limit/isolasi eksisting otomatis berlaku karena semua jalur internal sudah ber-kunci ownerUserId.
  • Tool yang diekspos (v1):
    MCP toolDelegasi internal
    verify_statisticssandboxRunner.runStatVerification — input: file/teks paper; output: computationChecks + ringkasan
    verify_citationsModul sitasi 4-langkah — input: bibliografi/daftar DOI; output: integrityStatus per item
    run_computationrunSandboxTask ber-taskKind — kuota lebih ketat, job panjang mengembalikan workflowId + tool get_run_status untuk polling
    search_scholarlyKomposisi OpenAlex/Crossref/arXiv eksisting (nilai tambah: sudah ter-cache, ter-rate-limit sopan, ter-normalisasi)
  • MCP client (fase akhir, opsional): kerangka yang sama dibalik — agen Astra mengonsumsi MCP server eksternal (manajer referensi Zotero, registry dataset) sebagai tool tambahan; arsitektur tool-injeksi-per-call membuat ini tinggal satu builder lagi.

Roadmap Implementasi

Lima fase berurutan; setiap fase mandiri nilainya dan bisa dirilis. Estimasi relatif (S/M/L) — bukan kalender, karena kapasitas tim tidak diketahui.

Fase 0Pelunasan · M

Perbaikan audit kritis & konsolidasi

  • AUD-01 guard server-side executeArtifact · AUD-02 agentKind di usage handler · AUD-03 kontrak tipe deep-start · AUD-04 cache sebelum gate biaya.
  • AUD-05 injeksi citation counter per giliran · AUD-06/21 konstanta bersama (HITL names, markers, sentinel, USER_AGENT) · AUD-11 bersihkan skema.
  • Test kontrak untuk routing/HITL/billing — fondasi suite eval Fase 3.

Keluaran: basis yang aman untuk ditambah jalur eksekusi baru. Tidak ada fitur baru, tidak ada perubahan UX.

Fase 1Sandbox · L

Lapisan Daytona + verifikasi statistik (fitur #1)

  • Bangun snapshot riset (Python+R), pola tiga-file (sandboxRunner "use node" → sandboxTools → registrasi messages.ts), tabel sandboxRuns/computationChecks, feature billing sandbox_compute.
  • Compute Router deterministik + tool verifyStatistics (auto) dan runComputation (approval, kartu informed-consent).
  • Pipeline statcheck → GRIM/GRIMMER → power; penyajian netral; tautan replay run.
  • Job panjang via WorkflowManager (provision/hydrate/execute/persist/teardown sebagai step terpisah).

Keluaran: pengguna men-drop paper, bertanya "cek konsistensi statistiknya", dan menerima hasil recompute yang bisa direplay. Momen demo terkuat platform.

Fase 2Integritas · M

Verifikasi sitasi 4-langkah + integrasi ke deep research

  • Modul sitasi (komposisi OpenAlex/Crossref/arXiv eksisting) + kolom integrityStatus; tool chat verifyCitations; otomatis pada sumber final deep research.
  • Sisipkan tahap compute/verify ke workflow deep research (masih dalam struktur step lama): paper kuantitatif → ekstrak angka utama + cek integritas ringan secara default.
  • Panel Verifikasi v1 di UI: verificationReport ringkas, badge per sumber, badge evidenceStrength yang selama ini tak terpakai (AUD-19).
  • Agent Skills runtime v1: tabel skills/skillActivations, parser+validator SKILL.md, katalog tier-1 di context assembler, tool activate_skill (enum) + read_skill_resource, proteksi kompaksi. Seed 4–6 skill builtin: deep-research-guide, stat-verification, citation-verification, citation-apa7, academic-id.

Keluaran: laporan deep research berubah dari ringkasan menjadi ringkasan yang sudah tersaring kualitasnya — klaim positioning terpenuhi end-to-end.

Fase 3Orkestrasi · L

Dekomposisi multi-agent + upgrade auditor + evals

  • Pecah researchLoop menjadi subagen ber-kontrak (literatur, counter-evidence, statistik ⇄ sitasi paralel, penulis, auditor) sebagai workflow step; anggaran per-subagen; event observabilitas baru.
  • Upgrade auditor: model per-tier, batch paralel, bukti komputasional, claimSpan (AUD-10, Modul 3).
  • Suite eval CI: golden set statistik + sitasi + skenario routing/HITL + eval pemicu skill (deskripsi memicu pada prompt relevan, diam pada yang tidak — sesuai panduan evaluating-skills agentskills.io); perbaikan AUD-13–17 yang tersentuh refactor.
  • Skills fase domain: delegasi subagen (tiap subagen mengaktifkan skill-nya), paket domain pertama (deep-research-medis, -cs-ml, -pendidikan), migrasi 10 slash command ke skill builtin, upload skill user/workspace via UI + informed-consent skill ber-skrip.
Fase 4Ekspansi · L

MCP server + replikasi (fitur #2) + meta-analysis (fitur #3)

  • Endpoint MCP di Convex HTTP actions (verify_statistics, verify_citations, run_computation, search_scholarly) + API key per-user.
  • Workflow replikasi paket reproducibility: tarik repo data+kode → jalankan di sandbox (egress allowlist) → bandingkan hasil utama → laporan reproduksi.
  • Workflow systematic review/meta-analysis: ekstraksi effect size → pooled estimate (metafor) → forest/funnel plot → uji heterogenitas → deteksi publication bias; output artifact + verificationReport.
  • Ekosistem skills: pustaka skill domain terkurasi sebagai konten produk (termasuk skill jurnal target & konvensi akademik ID), impor skill komunitas (validasi skills-ref + review), ekspor skill Aqsha sebagai folder standar — portabel ke Claude Code/Codex/Gemini CLI.
  • Opsional: MCP client untuk tool eksternal; evaluasi adopsi A2A bila kebutuhan kolaborasi eksternal muncul.

Dependensi yang mengikat urutan

Fase 1 bergantung pada Fase 0 (jalur eksekusi baru di atas gating yang masih rapuh = memperbanyak permukaan AUD-01/02/03). Fase 2 modul sitasi tidak bergantung Fase 1 dan bisa dikerjakan paralel bila ada kapasitas. Fase 3 sebaiknya tidak dimulai sebelum Fase 2 stabil — refactor besar di atas pipeline yang belum teruji menggandakan risiko regresi.
