# Deep Research artifact delivery controls

Aqsha treats the Artifact Manifest as the source of truth for visual artifacts embedded in a Deep Research final Markdown report. A run may produce a Multi-visual Final Report with several audited PNG artifacts, and each artifact is embedded only when its audit status is `passed`. Optional visual failures become Visual Omission records in the Research Trail and audit metadata, not notes in the final Markdown report, while a Primary Visual Deliverable failure can fail the run.

Deep Research uses phase-aware retry for render and upload failures before retrying earlier research phases. Retry attempts are recorded as new attempts linked to the original phase, visual ID, or artifact lineage instead of overwriting history. V1 manual and automatic phase-aware retry is limited to render and upload failures. Delivery retry stays inside the same Deep Research Run while the existing Evidence Ledger, Visual Spec, PNG checksum, and Artifact Manifest lineage remain valid. Citation audit or evidence-validity failures end the run with a Failure Summary or require a Derived Research Run rather than a narrow delivery retry. A Derived Research Run is used when the user continues after cancellation, changes scope or evidence, or needs a different Research Decision. The V1 automatic retry limit is one transient retry for render or upload. Automatic retry is only used for likely transient failures such as sandbox timeout, temporary artifact retrieval failure, or temporary UploadThing failure; deterministic failures such as validation, invalid Visual Spec, model/tool misuse, unsupported script, or citation/evidence audit failure stop with a Failure Summary.

Retry Attempt is persisted as Research Trail events plus run/artifact metadata in V1, not as a separate user-facing table. Delivery retry events include `delivery_retry_started`, `delivery_retry_succeeded`, and `delivery_retry_failed` with payload fields for `attemptNumber`, `phase`, `visualId`, artifact lineage, `errorClass`, and compact failure context. A dedicated retry table should wait until Aqsha needs a detailed retry inspection or replay UI.

Research Error Class is stored in run metadata for run-level failures and event payloads for phase or tool failures in V1. A dedicated database column should wait until Aqsha needs cross-run operational reporting or filtering by error class. User-facing failure messages stay provider-neutral unless the provider name is necessary for the user action; provider responses, stack traces, Daytona stderr, UploadThing details, and other debugging context stay in logs or internal Research Trail payloads.

Cancellation is requested through an explicit run-scoped endpoint such as `POST /threads/:id/runs/:runId/cancel`, not by canceling the latest run implicitly. This keeps cancellation idempotent and auditable when the UI is stale or multiple run records exist. Delivery retry is requested through a narrow endpoint such as `POST /threads/:id/runs/:runId/retry-delivery` with `phase` limited to `render` or `upload`, plus optional `visualId` or `artifactId`. The API rejects retry when run state, Evidence Ledger, Visual Spec, PNG checksum, or Artifact Manifest lineage is no longer valid.

Cancellation uses `cancel_requested` only as a transition state and `canceled` as the terminal state. While a run is `cancel_requested`, it is still in-flight and blocks new runs in the same Research Chat until the API orchestration layer marks it terminal `canceled`. Astra, Research Sub-agents, trusted scripts, renderers, and artifact publishing clients may observe cancellation and stop work, but only the API orchestration layer owns the terminal run status transition. Cancellation is propagated to model streaming, Research Sub-agents, sandbox execution, rendering, and artifact publishing where providers support it. Canceled runs are not resumed automatically in V1; later continuation should create a derived run.

Cancellation is recorded with three stable Research Trail events: `run_cancel_requested` when the API accepts the cancel intent, `run_cancellation_propagated` when active boundaries have received or rejected propagation, and `run_canceled` when the terminal status is written. The propagation event payload records each active boundary as `propagated`, `unsupported`, or `already_finished`. User-requested cancellation is not recorded as `run_failed`; only a system bug while processing cancellation should create a failure event.

If cancellation intersects artifact publishing after UploadThing has returned a `fileKey` or URL but before the artifact is validly persisted, the file is treated as an Orphan Published Artifact. The system attempts best-effort cleanup through the upload client and records `orphan_published_artifact_cleanup_failed` if cleanup fails.

This trades a simpler single-chart/single-run model for auditable artifact delivery that can handle real final reports with multiple visuals. It also avoids repeating source discovery for narrow delivery failures while preserving enough event history to debug retries, omissions, orphan published artifacts, and classified failures.
