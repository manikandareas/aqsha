Agent core configuration & runtime (Astra Lite / Astra Pro)

Two @convex-dev/agent v0.6.1 Agent instances (astraLite, astraPro) over a shared components.agent store, differing only in model, step budget, and intro instructions, fed by env-driven model selection and an OpenAI-compatible provider, with a UsageHandler that records token usage to billing.

This component is the heart of the Aqsha agent subsystem: it constructs the two "Astra" agents used for all chat generation. runtime.ts builds astraLite and astraPro via new Agent(components.agent, {...}) (runtime.ts:42, runtime.ts:49). Both are instances of the @convex-dev/agent v0.6.1 Agent class (which wraps Vercel AI SDK v5/v6 streamText/generateText) bound to the SAME components.agent component store — so they share threads, messages, and streams. The only differences are languageModel, stopWhen (step budget), and the per-tier intro lines prepended to a shared instruction block.

The constructor's option object (typed Config & { name; languageModel; instructions?; tools?; stopWhen? } per the agent package's index.d.ts:50-82) controls: name (attributed on each message this agent writes — "Astra Lite" / "Astra Pro"), languageModel (the AI SDK LanguageModel for every generate/stream call), instructions (default system prompt injected into each request, overridable per-call via system), and stopWhen (a StopCondition controlling the agentic multi-step loop). Tools are NOT set on the agent here — they are injected per-call in messages.ts (runInlineGeneration), so the agent objects are tool-agnostic shells. Note usageHandler is a valid Config field but is NOT set on the agent instances; instead recordUsage is passed per-call as usageHandler to streamText (messages.ts:1037).

models.ts is the single source of truth for model selection, resolving each tier through a preferred → legacy → hardcoded-default chain off process.env. providers/providers.ts builds two OpenAI-compatible providers (chatProvider, embeddingProvider) via createOpenAI from env-driven base URL / API key / provider name. recordUsage (a UsageHandler) translates the AI SDK usage payload into a billing/usage mutation.

The two other listed files are mislabeled by the review brief: providers/providerCache.ts actually contains the external research Provider type union + providerValidator (openalex/crossref/arxiv/exa/jina_*/explore/paper_ingest/google_factcheck/gdelt) — it is NOT a provider cache and is unrelated to LLM provider caching. agent/rateLimits.ts contains two public queries (getSendStatus, getServerTime) that surface the sendMessage rate-limit status to the composer; the real rate-limiter config lives in convex/limits.ts.

Data flow›
  1. Module load (providers.ts): openAiCompatibleProviderConfig reads env to build chatProviderConfig/embeddingProviderConfig, then createOpenAI produces chatProvider and embeddingProvider. models.ts resolves CHAT_LITE_MODEL/CHAT_PRO_MODEL (and deep variants) via preferred→legacy→default env chains.
  2. Agent construction (runtime.ts): astraLite = new Agent(components.agent, {name, languageModel: chatProvider.chat(CHAT_LITE_MODEL), instructions: LITE_INSTRUCTIONS, stopWhen: stepCountIs(5)}) and astraPro (CHAT_PRO_MODEL, PRO_INSTRUCTIONS, stepCountIs(10)). Both bind the SAME components.agent store. astra = astraLite is the neutral alias.
  3. Instructions assembly: LITE_INSTRUCTIONS/PRO_INSTRUCTIONS = [tier-specific intro lines, ...SHARED_INSTRUCTIONS].join(' ') → a single system string set as the agent's instructions (default system prompt, overridable per call via system).
  4. A send (messages.ts send/startThread → savePromptAndScheduleRun → scheduleGenerationForMessage) saves the user message and schedules generateReply.
  5. Generation (runInlineGeneration): picks agent = agentForKind(agentKind); builds per-call tools (normalChatTools + HITL tools) and activeTools (withholds executeArtifact on the first turn); calls agent.streamText(ctx, {threadId,userId}, {promptMessageId, tools, prompt?, activeTools?}, {saveStreamDeltas, usageHandler: handleUsage}). The agent's own instructions + stopWhen govern the multi-step loop; tools/activeTools and usageHandler come from this call.
  6. Step loop: the agent runs Vercel AI SDK streamText; each tool-call+result and follow-up generation counts as a step; the loop halts when stopWhen (stepCountIs(5)/(10)) is satisfied or the model emits a final assistant message.
  7. Usage accounting: after each LLM response the AI SDK fires usageHandler → recordUsage (runtime.ts) with {userId, threadId, provider, model, usage}. It computes input/output/total tokens and runs internal.agent.messages.recordUsage.
  8. Billing mutation (messages.ts:1722): soft-debits globalTokenUsage (observe-only, never throws), derives feature (pro_chat iff model===CHAT_PRO_MODEL else normal_chat), inserts a usageLedger row, and calls recordProviderUsage with estimateCredits to debit plan credits.
  9. Status surface: independently, rateLimits.ts getSendStatus lets the composer poll the sendMessage rate-limit (ok / retryAt) without sending.

Design decisions9›
Two Agent instances over one shared components.agent store, differing only in model/stepBudget/intro instructions.
Why Lets the composer toggle lite↔pro per message while keeping a single thread/message history; agentForKind dispatches and astra=astraLite handles agent-neutral store ops (saveMessages, titles, failures).
Tools are NOT configured on the Agent constructor; they're injected per streamText call (messages.ts).
Why The same agent must expose different tool surfaces per turn (first turn withholds executeArtifact via activeTools; resume turn includes it; deep-research turn exposes only startDeepResearch). Per-call tools keep the agent a thin shell.
usageHandler passed per-call (streamText 4th arg) instead of on the Agent.
Why Keeps the agent definitions pure/config-free and lets generation code own the billing wiring; recordUsage is shared by both tiers.
Shared instruction block with per-tier intro lines only.
Why Guarantees identical tool/citation/HITL/artifact/workspace behavior across tiers; only answer length/posture (focused-efficient vs thorough-rigorous) varies.
Step budget is double for pro (10 vs 5).
Why Pro is meant for deeper multi-tool reasoning; lite is capped to stay fast/cheap. Both override the agent package's default of maxSteps=1.
Model selection via preferred→legacy→hardcoded-default env chain.
Why New tier-aligned env names (AQSHA_CHAT_LITE/PRO_MODEL) while still honoring legacy AQSHA_NORMAL/PRO/DEEP_MODEL so existing deployments keep working; defaults match prior behavior exactly.
recordUsage internal mutation is observe-only and never throws.
Why It runs in the usage handler AFTER the reply is generated; throwing would crash a completed reply. globalTokenUsage uses throws:false plus a try/catch around the 'count exceeds capacity' component error.
OpenAI-compatible provider via createOpenAI with optional base URL + 'none' auth mode.
Why Supports self-hosted/gateway OpenAI-compatible endpoints: when only a base URL is set (no key), apiKey is '' (auth 'none') and the provider is still enabled.
deepModelForAgent treats undefined agentKind as 'pro'.
Why Legacy/in-flight deep-research runs queued before agentKind existed must keep the old (pro) default for both generation and the upfront billing estimate so they never diverge.
Gotchas & sharp edges8›
  • The review brief mislabels two files. providers/providerCache.ts is NOT an LLM provider cache — it only defines the external-research Provider union + validator (crossref/openalex/arxiv/exa/jina_*/explore/paper_ingest/google_factcheck/gdelt). agent/rateLimits.ts only contains getSendStatus/getServerTime queries; the rate-limiter definitions live in convex/limits.ts.
  • usageHandler is a valid Agent Config field (types.d.ts:105) but is intentionally NOT set on astraLite/astraPro. Usage accounting only happens because recordUsage is passed per-call to streamText (messages.ts:1037). A new call site that forgets to pass it would silently skip billing/usage recording.
  • stepCountIs counts AI-SDK steps, not LLM round-trips intuitively: a tool call+result is one step and the follow-up generation is another, so stepCountIs(5) is roughly 2-3 tool uses before forced stop. If it stops mid-loop, the last step result may not be an assistant message (agent docs).
  • Agent package default maxSteps is 1; without the explicit stopWhen, tools would barely loop. The behavior depends entirely on stepCountIs being set here.
  • recordUsage derives the billed feature purely from the model string (pro_chat iff model===CHAT_PRO_MODEL). If CHAT_PRO_MODEL and CHAT_LITE_MODEL are ever set to the same env value, pro usage would be billed as normal_chat.
  • models.ts reads process.env at module load, so the resolved CHAT_LITE/PRO_MODEL constants are frozen for the deployment's lifetime — changing env requires a redeploy/cold start, not a hot reload.
  • providers also read env at module load; with no key and no base URL, auth is undefined and apiKey is undefined — createOpenAI would then rely on its own OPENAI_API_KEY default, and enabled is false (used by RAG/embedding gates).
  • astra.ts (sendPrompt) uses generateText (non-streaming, no tools, lite alias) — it is a smoke test, not the production path; production uses streamText in messages.ts.

Message send/generate/stream orchestration (agent/messages.ts)

The chat-turn engine: public send/startThread mutations save the user prompt + consume quota, schedule generateReply, which runs agent.streamText with a tool surface gated by activeTools (executeArtifact withheld on the initial turn), persists sources/run-status, and releases the composer via markThreadIdle.

This module (~1781 lines) is the heart of a single Astra chat turn on the Convex + @convex-dev/agent stack. It owns the entire lifecycle from a user pressing send to the assistant reply landing and the composer being released. The public entry points are two Convex mutations — startThread (new thread) and send (existing thread) — plus the list paginated streaming query. A mutation validates/authorizes the user, charges credits + rate limits up front (checkAndConsumeSendQuota), saves the user message through the agent component (astra.saveMessages), writes side-channel metadata (rich mention content, command metadata, context artifacts/workspaces), then schedules the actual LLM work onto the Convex scheduler.

The generation itself runs in internalActions (generateReply, resumeGeneration, generateDeepPlan) that all funnel into the shared core runInlineGeneration. That core optionally prepends RAG context, assembles the tool surface (buildGenerationTools = normalChatTools + HITL tools, or buildDeepResearchTools for deep planning), computes the activeTools gate (the key trick: on the initial turn executeArtifact is withheld so the model must go through an approved proposeArtifact first), and calls agent.streamText(...) with saveStreamDeltas chunking and a usageHandler. After the stream drains it detects native HITL pauses (hasPendingNativeHitl over the AI-SDK steps), persists cited sources, and transitions the run + thread status.

Run lifecycle is tracked in the agentRuns table with statuses queued | running | waiting | completed | failed | canceled (the inline path uses running/waiting/completed/failed; deep runs start queued). The mutations startInlineRun, completeInlineRun, failInlineRun, patchRunStatus, markThreadIdle, and markThreadFailed move the run and the threadMetadata.status (idle | streaming | failed) so the frontend composer knows when a reply is in flight. markThreadIdle/markThreadFailed are race-guarded by hasOtherActiveReplyRun so a stale older run cannot clobber a newer in-flight one.

Deep research is dispatched out of band: when the resolved prompt's executionKind === "deep_research", scheduleGenerationForMessage calls deepResearch.startForMessage instead of the inline path; that creates a mode:"deep", executionKind:"workflow" run (status queued) and schedules generateDeepPlan, which streams a planning turn whose only active tool is startDeepResearch (needsApproval). Usage is billed twice: an estimate up front in the mutation and the real provider usage in the usageHandler (recordUsage).

Data flow›
  1. User sends a prompt -> public mutation send (existing thread) or startThread (new). requireCurrentUser, validateContent (<=8000 chars), and for send a hasActiveReplyRun guard returning reply_in_progress.
  2. checkAndConsumeSendQuota: estimate tokens (len/4), choose feature (deep_research | pro_chat | normal_chat) + requiredPlan, consumeCredits, then check+consume rate limits (sendMessage per-user, globalSendMessage, globalTokenUsage). Failure returns a typed {ok:false} (rate_limited / quota_exceeded / subscription_required / billing_inactive).
  3. savePromptAndScheduleRun: add thread context, strip mention markers, resolvePromptPayload, astra.saveMessages({role:user}), persist messageRichContent / messageCommands / context artifacts+workspaces, upsertThreadMetadata(status:'streaming'), update thread title from prompt.
  4. scheduleGenerationForMessage: build generation prompt (thread context + expandedPrompt). If executionKind==='deep_research' -> deepResearch.startForMessage (createRun status 'queued', schedules generateDeepPlan) and return its runId. Else -> startInlineRun (insert agentRuns status 'running') + scheduler.runAfter(0, generateReply, {...runId, prompt, visiblePrompt}).
  5. generateReply (internalAction) verifies thread ownership, calls runInlineGeneration({includeExecuteArtifact:false, scheduleTitle:true}).
  6. runInlineGeneration: optionally prepend RAG context; assemble tools (buildGenerationTools); compute activeTools = all normalChat keys + HITL_TOOL_NAMES (executeArtifact withheld); agent.streamText(ctx, {threadId,userId}, {promptMessageId, tools, prompt?, activeTools?}, {saveStreamDeltas:{chunking:'word',throttleMs:100}, usageHandler:handleUsage}).
  7. result.consumeStream() drains deltas (persisted incrementally for the list streaming query). Read result.text, result.steps, result.savedMessages.

Design decisions8›
Withhold executeArtifact on the initial turn via activeTools = [...normalChatTools keys, ...HITL_TOOL_NAMES] (executeArtifact excluded), only enabling it on resume (includeExecuteArtifact:true).
Why Forces the model through an approved proposeArtifact (needsApproval) before any artifact write, so it cannot silently write/overwrite an artifact in one turn. executeArtifact itself is NOT approval-gated; the gate is purely the activeTools surface.
Single shared core runInlineGeneration drives initial turn, HITL resume, and deep planning, parameterized by includeExecuteArtifact / deep / scheduleTitle.
Why Keeps stream handling, source persistence, run-status, and error handling identical across the three entry actions; deep vs normal only changes tool surface + post-stream branch.
Two-table run model: inline runs use completeInlineRun/observations; deep runs use patchRunStatus + the workflow step model.
Why Deep research lifecycle is owned by the durable workflow (handleWorkflowComplete), so messages.ts must NOT call completeInlineRun for deep runs — patchRunStatus is the minimal hook it keeps.
markThreadIdle / markThreadFailed are guarded by hasOtherActiveReplyRun (and reply-in-progress by hasActiveReplyRun), scanning the last 8 runs.
Why Prevents a finishing older run from flipping the thread to idle/failed while a newer reply is still streaming; concurrency safety for overlapping sends.
Usage is billed twice: an up-front estimate (consumeCredits with estimateTokens) and the real provider usage in the usageHandler (recordUsage).
Why Up-front estimate gates entry (can reject before spending); the post-reply handler records actual tokens for ledger/credits without ever throwing (it runs after the reply is already generated).
recordUsage wraps globalTokenUsage soft-limit in throws:false + try/catch and only logs.
Why The handler runs after a completed reply; throwing would crash a successful turn, so it is observe-only and treats the global limit as a system-wide safety signal.
Marked mention text is stored separately in messageRichContent while the agent sees clean stripped content.
Why The LLM gets clean text (no @mention markers) while the bubble renderer can re-render mention chips from messageRichContent.
Two-phase attachment flow: startThread saves the prompt with deferGeneration, then a scheduled processPendingAttachmentsAndStart -> completeThreadStartAfterAttachments resumes generation.
Why Uploads must be processed (parsed/indexed) before the model runs so attachments are available as RAG/thread documents; context persistence is idempotent by messageId to tolerate re-runs.
Gotchas & sharp edges10›
  • activeTools is the ONLY thing withholding executeArtifact on the initial turn — executeArtifact itself has no needsApproval. If activeTools were ever omitted/undefined on the initial turn (includeExecuteArtifact:true), the model could write an artifact in one shot without an approved proposeArtifact. The hitlTools comment references prepareStep gating, but the actual gate in this file is activeTools.
  • Run-status statuses differ by path: inline runs use 'running'->'waiting'/'completed'/'failed'; deep runs start 'queued' (createRun) then 'running' (startExecuteFromPlan). The runLifecycle.ts union also includes 'canceled', but messages.ts itself never sets queued/canceled. patchRunStatus only accepts running|waiting|completed (cannot fail a deep run).
  • markThreadIdle/markThreadFailed silently no-op if hasOtherActiveReplyRun is true — so if an older run finishes after a newer one already settled the thread, the thread status is intentionally not changed. Combined with the last-8-runs scan, >8 concurrent runs could miss an active run.
  • recordUsage derives the billed feature purely from the model string (CHAT_PRO_MODEL -> pro_chat) because the usage handler does not receive agentKind; if env model names overlap or CHAT_PRO_MODEL == CHAT_LITE_MODEL, pro usage could be mis-billed as normal_chat.
  • estimateTokens is a crude len/4 heuristic used for both the credit estimate and the globalTokenUsage rate count; real token usage can diverge significantly, and globalTokenUsage is only consumed (limit) for the real count post-reply, while the pre-send only checks it.
  • getVisibleAssistantMessageId relies on order/stepOrder grouping; if savedMessages ordering shape changes (AI SDK / component version), the citation anchor (and returned messageId for saveAssistantMessage) could attach to the wrong message.
  • The deep branch in runInlineGeneration detects success by scanning tool results for output.status === 'deep_research_started'; if startDeepResearch's execute return shape changes, the workflow could start while messages.ts still marks the run completed and releases the composer (double-completion).
  • On error runInlineGeneration saves FAILURE_TEXT then rethrows — the action still fails (for retry/observability) even though a user-facing message and failed status are persisted, so the scheduler may log the throw despite graceful UI handling.
  • PENDING_HITL_TOOL_NAMES includes executeArtifact and startDeepResearch beyond HITL_TOOL_NAMES, so an unresolved executeArtifact/startDeepResearch call is also treated as a pause (keeps run 'waiting'), even though executeArtifact has an execute handler.
  • generateReply/resumeGeneration/generateDeepPlan default agentKind ('lite' for reply/resume, 'pro' for deep plan) when missing, to tolerate legacy in-flight scheduled jobs queued before agentKind existed — so an in-flight job can silently use a different tier than intended.

Agent data model: schema tables + Convex component registration

App-owned Convex schema tables that back the agent/research subsystem (threads, runs, messages, sources, citations, usage) plus the five installed Convex components (agent, rag, rateLimiter, workflow, polar) registered in convex.config.ts; agent message bodies/threads/embeddings live inside the agent + rag components, not in this app's schema.

This component is the persistence layer for the Aqsha agent subsystem. schema.ts defines the app's own tables with { schemaValidation: true } (schema.ts:953). Crucially, the actual chat messages, thread records, and vector embeddings are NOT in this schema — they live inside the installed @convex-dev/agent and @convex-dev/rag components. This app's tables are sidecar/projection tables keyed by string threadId/messageId (the agent component's external IDs) and by ownerUserId (the Clerk-derived owner key, NOT a v.id("users")). Every app table partitions on ownerUserId as the first index column, giving per-user data isolation by convention.

The data flow centers on a thread: threadMetadata (schema.ts:130) mirrors per-thread state (last activity, message count, status, sticky agent kind) for the agent component's threads. When a user sends a message, an agentRuns row (schema.ts:370) is created to track the run lifecycle (inline vs workflow execution, deep-research rounds, sufficiency/verification status, budgets). Research-specific runs share the same runId union (v.union(v.id("agentRuns"), v.id("researchRuns")), schema.ts:7) but researchRuns is referenced only via that union — there is NO researchRuns table defined in this schema, so a v.id("researchRuns") is a dangling/forward reference to a table not present here (a notable gotcha).

Around each message the schema stores projections: messageCommands (slash-command runs), messageWorkspaceArtifacts/messageWorkspaceActions (workspace side effects), messageContextArtifacts/messageContextWorkspaces (context snapshots for the bubble), messageRichContent (user text with mention markers), and messageArtifacts (artifact version links). Research evidence is captured in researchSources, researchExtracts, and citationChecks. Token/credit accounting is split across usageLedger (legacy per-message token ledger), providerUsageLedger (credit-feature ledger), and usageDailyRollup (denormalized per-(owner,UTC-day) rollup maintained atomically with each ledger insert). convex.config.ts registers the five components that the agent runtime, RAG context, rate limiting, durable workflows, and Polar billing depend on.

  2. The user sends a message. The agent component persists the message body; this app stores the user's marked-up text in messageRichContent (schema.ts:363) plus context snapshots in messageContextArtifacts (schema.ts:338) and messageContextWorkspaces (schema.ts:352).   3. An agentRuns row (schema.ts:370) is created with executionKind inline or workflow. If a slash command triggered it, a messageCommands row (schema.ts:295) is written. If workflow, workflowId links to the workflow component (index by_workflow).
  4. Run progress is recorded as agentRunSteps (schema.ts:432) and agentRunEvents (schema.ts:456). For deep research, per-round state goes to researchRoundStates (schema.ts:482) with sufficiencyStatus.
  5. Discovered sources are written to researchSources (schema.ts:744) keyed by runId+sourceKey; quoted evidence to researchExtracts (schema.ts:800). Provider lookups are rate-limited via the rateLimiter component and cached in externalLookupCache (schema.ts:819).

  7. Verification: citationChecks (schema.ts:708) records per-claim support against sourceIds(researchSources)+extractIds(researchExtracts); results roll up into agentRuns.verificationStatus.

Design decisions6›
String threadId/messageId foreign keys to the agent component, not Convex v.id() references
Why The real thread/message rows live inside the @convex-dev/agent component (separate component namespace), so app sidecar tables can only reference them by the component's opaque string ids; all message/thread projection tables (threadMetadata, messageRichContent, message*) use v.string().
Every app table partitions on ownerUserId as the first index column
Why ownerUserId is the Clerk-derived owner key (string, not v.id('users')); using it as the leading index field gives per-user data scoping and bounded queries without a relational join.
Shared runId = union(agentRuns, researchRuns) across many tables
Why Lets steps/events/sources/extracts/citationChecks/usage attach to either a normal agent run or a research run with one validator; but researchRuns is not defined in this schema (forward/dangling reference).
Denormalized usageDailyRollup maintained atomically with providerUsageLedger inserts
Why Bounds the cost of the usage.activity query to a string-range window read on by_owner_date instead of scanning the entire ledger (perf optimization per commits 98d2f56/84daddd).
Split message side-effect/context into many narrow tables (messageCommands, messageWorkspaceArtifacts, messageWorkspaceActions, messageContextArtifacts, messageContextWorkspaces, messageRichContent, messageArtifacts)

Prompt parsing, slash-commands, and routing (normal vs deep / agent kind)

Slash-command catalog + parser that compiles user input into a visible-vs-expanded prompt payload, infers/auto-routes workspace and artifact commands, and decides inline-chat vs deep-research execution; agentKind (lite/pro) is selected upstream by the composer, not by this parser.

This component is the front door of the Aqsha agent subsystem's message path. It owns three concerns: (1) a static catalog of Indonesian academic slash-commands (promptCommands.ts), (2) parsing raw composer text into a structured PromptPayload that separates what the user sees from the expanded system-style instruction sent to the model (promptPayload.ts), and (3) routing — deciding whether a message runs as inline chat or as deep research, and (auto-)selecting the /artifact or /workspace HITL commands when the user didn't type a slash (promptRouting.ts + the two *CommandInference.ts helpers).

Routing has two orthogonal axes. The first axis, execution kind (inline vs deep_research), is derived purely from the command's mode field: only /deep-research (and its alias /deep) has mode: "deep", everything else is mode: "normal" → inline. This is computed by promptExecutionKindForCommand. The second axis, agent tier (lite vs pro = Astra Lite / Astra Pro), is NOT decided here — it arrives as the explicit agentKind mutation arg from the composer toggle and is threaded straight through messages.ts to agentForKind/chatModelForAgent/deepModelForAgent. So the four-way matrix (normal-lite, normal-pro, deep-lite, deep-pro) is the cross-product of command-mode (this component) and the caller-supplied agentKind.

Command parsing is two-pronged. Explicit commands: the composer may pass an explicit commandId, OR the raw text may literally begin with a slug/alias, detected by findExplicitPromptCommandInContent (promptCommandParsing.ts). promptPayloadFromCommand strips the slug, runs the command's buildPrompt(argument) to produce the expanded prompt, and records commandMetadata (label, slug, mode, argument preview, expanded snapshot). Auto-routing: when no commandId and no explicit slug is present, resolveAutoRoute uses keyword/regex intent detectors to silently route a free-text message to the /workspace command (create/rename intents) or the /artifact command (create/update/delete intents, gated on the thread having selected workspace-document context). Auto-routed payloads carry the full original text as both visible and argument, and appendRoutingHint glues a generated routing-hint block (listing target IDs and HITL tool instructions) onto the expanded prompt.

@workspace / @ws:item mentions are NOT extracted from text in this component. Mentions are resolved client-side (apps/web/lib/context-refs.ts) into explicit mutation args (selectedContextWorkspaceIds, selectedContextArtifactIds, messageAttachmentArtifactIds) plus inline private-use-area pill markers (U+E000/U+E001) embedded in content. This component's only mention handling is stripMentionMarkers (in mentionMarkers.ts), which removes those sentinels so the agent message stays clean while the marked text is stashed separately in messageRichContent for the bubble renderer. The selected workspace/artifact IDs feed pinned thread-context tables, and the FIRST @workspace auto-files a new thread.

Design decisions8›
Execution kind (inline vs deep) is derived solely from the command's static mode field, not from heuristics on the text.
Why Makes deep-research opt-in and explicit (only /deep-research or /deep), so quota/billing (isDeep) and the workflow dispatch are deterministic and can be computed upstream before the payload is even built.
agentKind (lite/pro) is a caller-supplied mutation arg, deliberately NOT decided in this parser.
Why Tier is a user-facing composer toggle (Astra Lite/Pro) independent of which slash-command runs, so the full normal/deep × lite/pro matrix is a clean cross-product; the parser stays tier-agnostic.
Two separate detection layers: findExplicitPromptCommandInContent (literal slug) gates auto-routing, while detect*Intent regexes drive it.
Why A user who types a real slash-command should bypass fuzzy auto-routing entirely; only free-text without a slug is eligible for intent inference, preventing double-routing.
Artifact auto-route is gated on the thread having selected workspace documents (selectedWorkspaceDocuments.length>0), workspace auto-route is not.
Why Mutating an artifact needs a concrete target; without a pinned doc there is nothing to update/delete, so artifact routing is suppressed. Workspace create/rename can stand alone.
Workspace keyword presence forces /workspace and explicitly excludes /artifact (WORKSPACE_KEYWORD_PATTERN returns null in artifact detector).
Why Disambiguates overlapping verbs (e.g. 'buat ... workspace' vs 'buat dokumen') so the two HITL command families never both fire on one message.
Routing hint is appended as plain text onto the expandedPrompt rather than passed as structured tool args.
Why The HITL tools are model-driven; the hint nudges the model toward the right tool and supplies artifactId/workspaceId inline, keeping the auto-route path identical to the typed-command path downstream.
visibleContent vs expandedPrompt split, with marker stripping and rich-content stashing.
Why The chat bubble must render exactly what the user typed (with @mention pills), while the model receives a clean, instruction-expanded prompt; the two are persisted separately (message text + messageRichContent + messageCommands).
Mentions resolved client-side into explicit IDs, not parsed from text server-side.
Why Avoids brittle server-side @-token parsing; the backend receives authoritative workspace/artifact IDs and only needs to strip the cosmetic inline markers.
Gotchas & sharp edges9›
  • agentKind is NOT inferred by this component — searching here for lite/pro detection logic is a dead end; it is the composer toggle passed straight through messages.ts to agentForKind. The parser only sets execution kind (inline vs deep).
  • deepModelForAgent and startExecuteFromPlan treat a MISSING agentKind as 'pro' (the old default), while generateReply/runInlineGeneration default a missing agentKind to 'lite'. The fallback differs by code path (legacy/in-flight jobs).
  • Auto-routing order is workspace-first, then artifact. A message containing the 'workspace'/'ruang kerja' keyword can never auto-route to /artifact (the artifact intent detector returns null on that keyword).
  • stripCommandSlug only strips when the slug is followed by a space or newline (or is the whole message). '/deepfoo' would NOT be treated as the /deep alias+arg — it falls through and the whole text becomes the argument with no command. findExplicitPromptCommandInContent has the same space/newline boundary requirement.
  • Auto-routed payloads set visibleContent to the FULL original text (the user never typed a slash), so the chat bubble shows their natural-language message, but commandMetadata is still recorded as commandId 'artifact'/'workspace' — the UI shows a command pill the user didn't type.
  • promptPayloadFromCommand throws ConvexError('Unknown prompt command') if commandId is set but unknown; resolvePromptPayload never re-validates an explicit commandId before this, so a bad explicit commandId from the client surfaces as a thrown error mid-send.
  • The /paraphrase alias '/parapharse' is a deliberate misspelling kept to catch a common user typo; do not 'fix' it.
  • Deep research does not generate the report inline: /deep-research first runs an inline PLANNING turn (generateDeepPlan) that proposes a plan via the startDeepResearch needsApproval tool; the actual research workflow only starts after user approval.
  • executeArtifact is intentionally withheld from the first-turn tool surface (activeTools) so an artifact write must pass through an approved proposeArtifact; it only becomes available on HITL resume.

This component is the "normal chat" (non-deep-research, non-HITL) tool surface for the two Astra chat agents. It is assembled as normalChatTools in research/researchTools.ts and merged with the HITL tool set by buildGenerationTools in messages.ts before being handed to agent.streamText. Four tools are exposed: searchThreadDocuments (semantic RAG over the user's uploaded/selected thread documents), and three external research tools searchWeb, searchArxiv, lookupDoi that are defined once in researchTools and re-exported by reference into normalChatTools.

The three research tools all return SourceCandidate[] (defined in research/sourceCandidates.ts). Each candidate is numbered through a citationCounter (monotonic next()), capped at the first 5 results per call by numberCandidates, and weak/empty results trigger fallbacks (web search falls back from Exa to Jina). After generation, collectSourceCandidates in messages.ts walks every step's toolResults, keeps array outputs whose items look like a SourceCandidate (citationNumber/title/locator/snippet), and persistCited records them against the assistant message together with the [n] markers the model actually emitted. searchThreadDocuments differs: it returns a plain string (RAG excerpt block) rather than candidates, so it feeds context rather than citations.

AqshaToolCtx extends the shared AgentToolCtx (ActionCtx & { userId?, threadId?, messageId? } from tools/toolContext.ts) with two optional research-only fields: runId?: Id<"agentRuns"> and citationCounter?: { next: () => number }. The userId/threadId fields are injected by the @convex-dev/agent component from the { threadId, userId } passed as the second arg to agent.streamText; requireToolUser/requireToolThread throw if absent. Notably, in the normal-chat path no call site populates citationCounter or runId on the ctx, so requireCitationCounter always falls back to a fresh createCitationCounter(1) per tool execution — citation numbers are per-tool-call, not globally unique across a turn.

The two command-inference modules (artifactCommandInference.ts, workspaceCommandInference.ts) are not tools; they are pure regex heuristics consumed by prompt/promptRouting.ts to auto-route a bare chat message to the /artifact or /workspace slash command (and thus to the HITL tools proposeArtifact/executeArtifact/deleteArtifact/createWorkspace/renameWorkspace). They detect create/update/delete (artifact) or create/rename (workspace) intent from Indonesian+English verb patterns and emit a routing-hint string that is appended to the prompt. artifacts.ts is the artifact persistence layer (Convex queries/mutations) the tools and UI read/write, not a tool itself.

Data flow›

User sends a chat message. resolvePromptPayload (promptRouting.ts) runs: if an explicit slash command is typed, it expands it; otherwise resolveAutoRoute tries workspace inference, then artifact inference (the latter requires selected workspace documents) and, on a hit, expands /artifact or /workspace and appends a routing-hint string to the prompt. This biases the model toward HITL tools — no tool is invoked yet.
  2. runInlineGeneration (messages.ts) builds RAG context via buildRagContextForThread and prepends it, then buildGenerationTools(promptMessageId) = { ...normalChatTools, ...buildHitlTools(...) }. activeTools may withhold executeArtifact on the first turn.
  3. agentForKind(agentKind).streamText(ctx, { threadId, userId }, { promptMessageId, tools, prompt, activeTools }, ...) runs.   4. Model decides to call a tool. For a source tool (searchWeb/searchArxiv/lookupDoi): handler reads userId via requireToolUser, obtains a citation counter (fresh fallback since none is injected), calls the relevant provider in externalProviders.ts (billing + rate-limit + 24h cache), maps results to candidates, numberCandidates caps to 5 and assigns sequential citationNumbers, returns SourceCandidate[]. Design decisions8›
Research tools defined once in researchTools and re-exported by reference into normalChatTools.
Why Single source of truth so deep-research and normal-chat tool sets share identical createTool instances; only searchThreadDocuments is normal-chat-specific.
AqshaToolCtx declares optional runId + citationCounter, but normal chat injects neither.
Why The same tool code is reused by deep-research (which does thread runId/citationCounter); in normal chat the citation counter harmlessly falls back to a fresh per-call counter, so numbers are per-tool-call rather than turn-global — a deliberate simplification, since collectSourceCandidates re-keys persistence by the markers the model emits.
Source tools return SourceCandidate[] and citations are harvested post-hoc from step outputs.
Why Decouples the model's free-text [n] markers from candidate generation; only candidates actually surfaced as array tool outputs become persisted citations, and only cited numbers are flagged via extractCitationNumbers.
searchThreadDocuments returns a context string, not candidates.
Why Uploaded/selected docs are user-owned context, not external sources to cite; returning a tagged excerpt block lets the model ground answers without polluting the citation list.
Exa→Jina fallback for web search gated by hasUsableResults.
Why Exa is primary; Jina is a resilient fallback when Exa returns weak/empty/unavailable results, improving answer grounding without a second paid call when Exa already succeeds.
Command inference is heuristic regex routing to slash commands, not a tool.
Why Lets users phrase artifact/workspace mutations naturally; auto-routing injects a hint that nudges the model into the HITL (needs-approval) tools so destructive/creative actions always get user confirmation. Read-only verbs and explicit slash commands are excluded to avoid hijacking normal Q&A.
Artifact auto-route requires selectedWorkspaceDocuments to be non-empty; workspace auto-route does not.
Why Artifact mutation needs a concrete target the user already pinned, avoiding accidental edits; workspace create/rename is self-describing from the prompt.
Two agents (lite/pro) share the same tool set and instructions, differing only in model + step budget.
Why Consistent tool/citation/HITL behavior across tiers; pro just gets more steps and a stronger model.

Human-in-the-loop (HITL) tools, approval, and resume

Native in-thread HITL on @convex-dev/agent: askUser (no-execute pause for an answer), needsApproval action tools (pause awaiting approval), and a propose→approve→executeArtifact two-step write flow, with pauses surfaced as unresolved tool parts and resume re-running generation with the full tool set.

This component implements the "native" human-in-the-loop model for the Astra chat agent. Instead of a separate FSM (the comments reference a retired hitlSessions/hitlCards design), HITL is expressed entirely through the AI SDK v5 tool-calling loop via the @convex-dev/agent component. The model triggers a pause simply by calling a HITL tool during ordinary generation. There are three pause shapes: (1) askUser has NO execute handler, so the AI SDK loop halts at the call with an orphaned tool-call awaiting a tool-result; (2) action tools (deleteArtifact, createWorkspace, renameWorkspace, startDeepResearch, and the display-only proposeArtifact) carry needsApproval: true, so generation pauses with a tool-approval-request part; (3) artifact writes are a two-step propose→approve→execute flow where proposeArtifact (approval-gated, display-only) is approved first and executeArtifact (NOT approval-gated, withheld on the initial turn via activeTools) does the actual write on resume.

The four files under agent/hitl/ define: the tool set (hitlTools.ts — buildHitlTools for chat tools and buildDeepResearchTools for the deep-research planning tool), the resume mutations called from the client (hitlResume.ts — answerAskUser, approveTool, denyTool, resumeHitl), workspace-resolution and artifact-guard helpers usable from query/mutation ctx (hitlWorkspace.ts), and internal provenance/guard functions that the action-context tools call via ctx.runMutation/ctx.runQuery because tools run in an ActionCtx and cannot touch ctx.db directly (hitlProvenance.ts).

These connect to agent/messages.ts, which owns the generation core. buildGenerationTools merges normalChatTools with buildHitlTools. HITL_TOOL_NAMES (askUser, proposeArtifact, deleteArtifact, createWorkspace, renameWorkspace) is the initial-turn HITL surface; executeArtifact is deliberately excluded so the model cannot write without an approved propose. PENDING_HITL_TOOL_NAMES = HITL_TOOL_NAMES + executeArtifact + startDeepResearch, used by hasPendingNativeHitl to detect a pause (a HITL tool call with no matching tool result). On the initial turn runInlineGeneration is called with includeExecuteArtifact: false, which sets activeTools = [...normalChatTools keys, ...HITL_TOOL_NAMES] (executeArtifact withheld); on resume includeExecuteArtifact: true leaves activeTools undefined so the full tool set (including executeArtifact) is offered.

The pause is surfaced to the UI as an unresolved tool part. hitl-parts.ts (hasPendingHitl) treats a part as pending when its state is approval-requested, or when it is askUser with state input-available. The composer is blocked (hitlBlocking) while any pending part exists. use-hitl-resume.ts records each resolution's messageId and fires resumeHitl only once hasPending flips to false (so all sibling approvals on a step are resolved before resuming, otherwise the component auto-denies unresolved siblings). Resume re-runs generation with promptMessageId pointing at the last resolved tool-result/approval-response so the answer is already in context. Design decisions6›
askUser has NO execute handler (instead of returning a placeholder).
Why A no-execute tool makes the AI SDK loop halt at the call with an orphaned tool-call, which is exactly the natural pause point; the answer is supplied out-of-band as a native tool-result. An outputSchema is still required so the component knows the supplied result shape.
Artifact writes are split into proposeArtifact (approval-gated, display-only) then executeArtifact (not approval-gated).
Why The approval card should review a plan, not the full body. executeArtifact is gated to the resume turn via activeTools so the model physically cannot write until an approved propose exists; the instructions also forbid calling executeArtifact before approval.
executeArtifact is gated by activeTools, NOT by needsApproval (and a stale code comment claims prepareStep).
Why Approval-gating executeArtifact would double-prompt the user (propose already approved). Withholding it from the initial-turn activeTools and only adding it on resume achieves the same safety with one approval. NOTE: the hitlTools.ts:45 comment says 'gated ... via prepareStep' but no prepareStep exists; the real mechanism is activeTools in runInlineGeneration.
resumeHitl is a separate step from answer/approve/deny; the client fires it only after hasPending flips false.
Why If a new generation starts while sibling approvals on a step are still unresolved, the component auto-denies them. Recording each decision first and resuming only when all are resolved (tracking lastMessageId) mirrors the component's reference UI and prevents accidental auto-denials.
Provenance + workspace guards are internal Convex functions in hitlProvenance.ts/hitlWorkspace.ts rather than inline in the tools.
Why Tools run in an ActionCtx and cannot touch ctx.db; the internal mutations/queries bridge to messageWorkspaceArtifacts/messageWorkspaceActions and the ownership/active/agent-writable guards, mirroring the side effects the retired hitlSessions completion path wrote.
Two agents (astraLite/astraPro) share one components.agent store, differing only in model and step budget (5 vs 10).
Why Keeps tools, citations, and HITL flows identical across tiers while allowing the Pro tier more reasoning/tool steps.

Two-layer context assembly: a synchronous mutation-time block (workspace manifest + pinned/attached/upload document bodies) prepended to the prompt, plus an async action-time RAG layer (@convex-dev/rag semantic search over artifactId/workspaceId filters) prepended just before agent.streamText.

Design decisions8›
RAG context is built in a separate Node action (ragContext.ts is 'use node') and prepended at action time, while the document/workspace block is built synchronously in the mutation.
Why Embedding the query + vector search requires the Node runtime and network I/O; doing it in the streaming action keeps the send mutation fast and lets the RAG query use the cleaned visible prompt. The two blocks are prepended at different times, so the final prompt carries the RAG block first, then the document/workspace block, then 'User message:'.
Workspace document *content* flows only through RAG retrieval; the manifest carries only names + titles, not bodies.
Why Whole workspaces could be huge; stuffing bodies would blow the budget. The manifest answers 'what's in this workspace' directly while bodies are retrieved semantically and bounded by RAG_CONTEXT_LIMIT (comment threadContext.ts:469-473, ragContext.ts:42-45).
RAG filters OR all artifactId and workspaceId entries; top-k is weighted (paper*2, workspace*4).
Why A single search retrieves chunks belonging to any pinned paper OR any active workspace, with workspaces given a bigger share since they contain many documents (ragContext.ts:42-65).
Only artifacts with ragEntryId AND indexingStatus==='ready' become artifactId RAG filters; url-type artifacts excluded.
Why Prevents searching against not-yet-indexed or non-indexable documents (threadContext.ts:622-633).
Active workspaces = filed-under (threadMetadata.workspaceId) + @mentioned, filed-under first.
Why A workspace-detail thread's workspace is included in both manifest and RAG even if never @mentioned, while explicit @mentions extend context (threadContext.ts:435-467, threadContextWorkspaces.ts:230-232).
Mention markers stripped before save/embed/RAG-query/title; marked copy stored separately in messageRichContent.
Why Keeps the model's prompt and the RAG query free of U+E000/U+E001 sentinels while preserving inline pill rendering in the UI (messages.ts:347-374, mentionMarkers.ts).
Per-message context snapshots (messageContextArtifacts / messageContextWorkspaces) are persisted idempotently by messageId.
Why Drives message-bubble badges and survives the two-phase deferred-attachment path without duplicating rows (threadContext.ts:727-830).
Chunking is delegated entirely to @convex-dev/rag defaults at ingestion time; this component never chunks manually.
Why Text is added whole (sliced to 300000 chars) via artifactRag.add; the RAG component splits/embeds it, and retrieval reassembles excerpts via chunkContext {before:1,after:1} (uploads.ts:545-562, ragContext.ts:66).
Gotchas & sharp edges9›
  • The prompt context is prepended TWICE in two phases: Phase-1 (document+workspace block via prependPromptContext, labeled 'User message:') happens in the mutation and is baked into the scheduled generationPrompt; Phase-2 (RAG excerpts) is prepended ON TOP in the action. Final order is: <retrieved_document_context> → <thread_document_context>/<thread_workspace_context> → 'User message:' → prompt.
  • RAG and document-body budgets are independent and additive (6000 RAG + 16000 bodies + the manifest), so total injected context can substantially exceed any single cap.
  • RAG retrieval is best-effort and silently degrades: any artifactRag.search error is caught and returns '' (ragContext.ts:80-83); if embeddingProviderConfig is disabled or the query is blank, RAG is skipped entirely with no signal to the model.
  • RAG runs only when BOTH prompt and visiblePrompt are present in runInlineGeneration (messages.ts:1001); the HITL resume path (resumeGeneration) passes no prompt/visiblePrompt, so it gets NO fresh RAG context.
  • An artifact only contributes an artifactId RAG filter if indexingStatus==='ready' AND it has a ragEntryId; a freshly uploaded, still-indexing doc is in <thread_document_context> (body) but invisible to RAG search until indexing completes.
  • Thread-only uploads are indexed with workspaceId='' (empty string) as the filterValue (uploads.ts:558-560), so they can only be retrieved via their artifactId filter, never via a workspaceId filter.
  • RAG_CONTEXT_LIMIT clipping collapses all whitespace to single spaces (clipText, ragContext.ts:109-115) and may truncate the last excerpt mid-sentence with an ellipsis.
  • Ingestion caps source text at MAX_INDEXED_TEXT_CHARS=300000 before chunking — content beyond ~300k chars is never embedded or retrievable.
  • listContextArtifactTargets de-dupes across selected/attachment/upload sources, but each source has its own cap; the effective artifact count fed to RAG top-k weighting (artifactTargets*2) is the count of READY, indexed, non-url artifacts only, not the raw selection.

This component is the evidence backbone of the Aqsha research agent. It standardizes every external result (Exa web, Jina search/read, arXiv, Crossref DOI) into a single SourceCandidate shape, scores each candidate on two independent axes — deterministic per-source content quality (assessSourceQuality) and statistical per-domain reliability (domainReliability) — and persists the surviving sources into the researchSources table keyed by a canonical content key so the UI can render a sources panel and map inline [1]/[2] citation markers back to concrete source rows.

There are two distinct persistence paths that both land in researchSources. (1) The inline reply path (messages.runInlineGeneration): tool steps from searchWeb/searchArxiv/lookupDoi emit arrays of SourceCandidate; collectSourceCandidates (messages.ts:1482) harvests them from step.toolResults, extractCitationNumbers regex-scans the assistant text for [n] markers, and sources.persistCited writes one row per deduped candidate, marking each usage: "cited" if its citationNumber appears in the text else "candidate". (2) The deep-research path (deepResearch.researchLoop → persistArtifact): a multi-round discover/rerank/read/validate loop produces accepted sources, upserts them incrementally via sources.upsertRunCandidates (usage candidate/accepted/rejected) keyed by run+sourceKey, and finally persistSourcesForRun writes the numbered final sources (usage: "accepted") linked to the report artifact, returning a citationNumber → researchSources._id map used to link citation checks.

Quality scoring (sourceQuality.ts) is purely deterministic and content-pattern based: it classifies a candidate as ok (readable / academic_abstract / sufficient_snippet) or not-ok (blocked / empty / metadata_only / provider_failure / too_short / duplicate) using regex blocklists and length thresholds. Reliability scoring (domainReliability.ts) is statistical and cross-run: every read attempt records a success/failure outcome per hostname; once a domain has ≥3 observations and a failure ratio >0.7 it is flagged unreliable and excluded from future discovery. The two "tiers" in this component are therefore the quality-reason union and the per-domain reliability boolean — there is no numeric composite score. evidenceStrength (strong/medium/weak) is a separate per-provider hint assigned at candidate creation (e.g. OpenAlex/Crossref with abstract → strong, Exa/Jina web → medium, provider-failure stubs → weak), carried through to the row and the UI type but not currently rendered as a visible badge.

Design decisions7›
Two scoring axes kept fully separate: deterministic content quality (assessSourceQuality, per-source) vs statistical domain reliability (domainReliability, cross-run).
Why Content quality must be reproducible and side-effect-free (used in multiple read/validate spots), while reliability needs accumulated history to penalize chronically-failing domains without over-reacting to a single failure (MIN_OBSERVATIONS gate).
No single numeric composite score; 'tiers' are the quality-reason union + reliability boolean + evidenceStrength enum.
Why Each signal drives a different decision (accept/reject, exclude-domain, provider hint), so a flat score would lose the actionable distinctions; rerankScore is the only numeric and is used only for ordering/relevance.
Canonical sourceKey (doi>arxiv>url>title) is the single identity across dedup, candidate-pool merge, upsert, and final persistence.
Why Lets the same physical source seen across providers/rounds collapse to one row and lets citationNumber→row mapping survive re-discovery; arxiv pdf/html→abs normalization prevents the same paper appearing twice.
persistCited deletes all prior rows for the message before re-inserting.
Why Inline replies can be regenerated; a full replace keeps the sources panel exactly consistent with the latest assistant text and avoids stale cited rows.
Citation numbers come from text-scanning ([n]) for inline, but index-based numbering (index+1) for deep research.
Why Inline answers cite ad-hoc within prose so the model's own [n] markers are authoritative; the deep report is synthesized against a fixed numbered source list, so deterministic 1..14 numbering keeps citationChecks.sourceIds aligned.
Unreliable domains are excluded at discovery time, not at read time.
Why Cheaper to never fetch them; reliability is advisory and updated continuously via recordOutcome on every read so flags self-heal as success ratio improves.
evidenceStrength assigned at provider/candidate creation rather than computed downstream.
Why The provider knows whether an abstract/summary was present (strong vs medium) and whether it is a failure stub (weak); this hint also gates the Exa→Jina fallback (hasUsableResults requires non-weak).
Gotchas & sharp edges9›
  • Two scoring systems can disagree: assessSourceQuality is per-call deterministic; domainReliability is global mutable state. A high-quality page on a flagged domain is silently never discovered because listUnreliableDomains pre-filters discovery.
  • evidenceStrength is persisted and exposed in the ResearchSource UI type but is NOT rendered as a visible tier/badge anywhere in apps/web (no component reads it for display) — only hasUsableResults consumes it (gating Jina fallback) and it is stored for potential future use.
  • Inline path citationNumber comes from a per-tool-call counter (numberCandidates, max 5 each) and is only meaningful if the model echoes the same [n] in prose; if the model cites a number no candidate carries, that [n] has no row, and conversely candidates whose number isn't cited persist as usage='candidate'.
  • persistCited fully deletes+reinserts per message, so any external augmentation of those rows would be lost on regeneration.
  • SourceQuality includes a 'duplicate' reason in its type union but nothing in this component ever returns it — dedup is handled separately by canonicalSourceKey, so 'duplicate' is effectively dead.
  • Deep-research final rows are written with usage='accepted' (persistSourcesForRun), never 'cited' — the UI treats listForThread rows and maps usage default to 'cited' in listForThread (row.usage ?? 'cited'), so a missing usage silently reads as cited.
  • domainReliability.recordOutcome is called once per read attempt inside recordReadAttempt; a source read via multiple fallback providers still records a single outcome keyed on quality.ok, so partial fallback successes count as success.
  • collectSourceCandidates only inspects array-valued tool outputs and uses a loose isSourceCandidate shape check (citationNumber+title+locator+snippet); a tool returning a non-array or differently-shaped payload contributes no sources even if it found evidence.
  • persistSourcesForRun uses insert-then-conditional-patch: on a fresh row it inserts, on an existing row it inserts NOTHING and patches — but the variable name sourceId is set before the patch, which is correct, yet the value object omits createdAt on patch (only set on insert), so createdAt is preserved only because patch doesn't touch it.

Billing or rate-limit failure throws a ConvexError and the network call never happens.

Results (including normalized failures) are persisted to the externalLookupCache table keyed by (provider, cacheKey) with expiresAt = now + 24h. Reads treat any row past expiresAt as a miss. Data flow›
  1. A research tool (Convex action) calls a provider function, e.g. searchExaCandidates(ctx, { ownerUserId, query, limit, ... }) or searchOpenAlexWorks(...), searchArxivProvider(...), lookupDoiProvider(...), jinaSearchWeb(...), jinaReadUrl(...), jinaRerank(...), getUrlContentProvider(...).
  2. The function trims/validates the query (empty query returns [] early; for Exa/OpenAlex the client/api-key presence is also checked early).
  3. Gate: limitExternal(ctx, ownerUserId, provider) (or limitOpenAlex) runs consumeCreditsInternal (feature external_search; crossref/arxiv pass credits: 1). If !billing.ok it throws ConvexError(billing.reason).
  4. Gate continues: Promise.all([rateLimiter.check(externalSearchPerUser, {key: userId}), providerRateCheck(...)]); if any blocked, throws ConvexError("External provider is rate limited"). Then Promise.all([rateLimiter.limit(externalSearchPerUser), providerRateLimit(...)]) consumes tokens.
  5. Cache check: build cacheKey (usually normalizeKey(JSON.stringify({...})); lowercased), call readCachedCandidates/readCachedJson -> getCache query. A row is a hit only if it exists AND expiresAt >= now. Hit returns parsed valueJson immediately (skips network — but NOTE the gate in step 3-4 already ran).
  6. Miss: build the request URL/body, set headers (User-Agent via userAgent() for arXiv/Crossref/OpenAlex; jinaHeaders injects Authorization: Bearer JINA_API_KEY when set; Exa client carries its own key), and fetch(...) the external API.
  7. !response.ok throws an Error(\<Provider> returned <status>\) (OpenAlex enriches with parsed body message). Otherwise parse: arXiv via XMLParser, Crossref/OpenAlex/Jina-JSON via response.json(), Jina text via regex block parsing.
  8. Normalize each result into an ExternalCandidate (origin, provider, evidenceStrength, title, locator, url, doi/arxivId, snippet via trimForSnippet, metadataJson). Filter nulls.
  9. Persist: writeCachedCandidates/writeCachedJson -> putCache mutation with status = failed | empty | ready, valueJson, optional failureReason, and expiresAt = now + 24h.
  10. On caught error: most providers build a normalized failure (providerFailure -> one weak "Provider unavailable" candidate, or readFailure for reader results), cache it with a failureReason, and RETURN it (no throw). Exceptions: searchOpenAlexWorks and getUrlContentProvider throw ConvexError.
  11. The action returns ExternalCandidate[] (or JinaReadResult / RerankResult[]), which the research pipeline later augments with citationNumber to become SourceCandidate[].

Design decisions9›
Single normalized ExternalCandidate shape (= SourceCandidate minus citationNumber) for every provider.
Why Lets the research pipeline merge arXiv/Crossref/OpenAlex/Exa/Jina results uniformly and assign citationNumber later; provider-specific extras ride in metadataJson (stringified).
Most providers normalize errors into a weak 'Provider unavailable' candidate (providerFailure / readFailure) and return rather than throw.
Why Keeps the agent tool loop resilient — a single provider outage degrades to a low-evidence placeholder instead of failing the whole research run. The failure is also cached so retries within 24h don't re-hit a broken API.
OpenAlex (searchOpenAlexWorks) and the Exa contents read (getUrlContentProvider) DO throw on failure.
Why OpenAlex is a primary scholarly source whose misconfiguration (missing API key) should surface loudly; getUrlContentProvider is a direct content fetch whose caller needs real text, so an empty/failed read is a hard error.
Two-tier rate limiting: a shared externalSearchPerUser bucket plus a provider-specific bucket, with global (keyless) buckets for crossref/arxiv/openalex.
Why Per-user fairness for paid features plus politeness toward shared external APIs; arXiv uses a fixed-window 1/3s to honor its documented etiquette, Crossref/OpenAlex use 30/min global pools.
Billing credits consumed BEFORE the cache check, inside the gate.
Why limitExternal runs unconditionally at function entry, before readCached*; a cache hit still consumed credits and rate tokens. This means cached results are not free — a deliberate (or at least load-bearing) ordering that meters every request, not every network call.
Cache keys are lowercased via normalizeKey(JSON.stringify(...)) of the salient args.
Why Stable dedup across whitespace/case variations; including limit/domains/dates/mode/fromYear ensures narrowing a filter refetches instead of returning a stale superset (explicitly noted for OpenAlex fromYear).
24h TTL with status (ready/empty/failed) and failureReason persisted.
Why Distinguishes 'no results' from 'broken provider' for observability while still short-circuiting repeated calls within a day.
Single Exa client factory and dual Jina parsing (JSON first, regex blocks fallback).
Why One API-key read site for Exa; Jina endpoints can return either JSON or markdown text depending on headers/version, so parsers defensively handle both.
OpenAlex abstract reconstructed client-side from abstract_inverted_index; select fields trimmed.
Why OpenAlex doesn't return plaintext abstracts; ?select= reduces payload size while still yielding enough for strong-evidence snippets and ExploreCandidateMetadata.
Gotchas & sharp edges11›
  • Billing credits and rate-limit tokens are consumed BEFORE the cache lookup (limitExternal/limitOpenAlex run at function entry, ahead of readCached*). A cache HIT still charges credits and burns rate-limit tokens — cached responses are not free and a hot cache can still trip the per-user 20/min bucket.
  • searchOpenAlexWorks does NOT wrap its fetch in try/catch (unlike every other provider): a network error, non-ok status, or missing OPENALEX_API_KEY throws and propagates instead of degrading to a providerFailure candidate. getUrlContentProvider similarly throws ConvexError on a failed read.
  • exaSearchPerUser bucket (10/min) is shared by BOTH searchExaCandidates and readWithExaContents (both pass provider 'exa'), so heavy content reads compete with web searches for the same per-user budget.
  • Jina reader appends the target URL raw after a slash (r.jina.ai/<url>) without re-encoding; URLs with query strings/special chars rely on Jina tolerating that. Jina search, by contrast, encodeURIComponent-encodes the query.
  • arXiv uses a GLOBAL fixed-window 1 request / 3 seconds bucket — under concurrency this is a hard cross-user bottleneck, not per-user; bursts will block with 'External provider is rate limited'.
  • USER_AGENT constant and userAgent() helper are duplicated verbatim in externalProviders.ts and openalexProvider.ts (drift risk).
  • Failure candidates are real entries in the returned array (origin from providerFailure, e.g. 'web'/'doi'/'arxiv', title 'Provider unavailable', locator = error reason). Downstream must call providerFailureReason to detect/strip them; otherwise an error message leaks as a 'source' locator/snippet.
  • Cache 'empty' vs 'failed' status both persist valueJson; an empty ready/empty result is cached for 24h, so a transient zero-result query won't be retried for a day even if the underlying corpus changes.
  • cleanDomains strips path and protocol and lowercases; a domain with a meaningful path or subdomain nuance may be over-normalized before being sent to Exa/Jina.
  • providerValidator / externalLookupCache enumerate 11 providers (incl. explore, paper_ingest, google_factcheck, gdelt) but this component only exercises openalex/crossref/arxiv/exa/jina_*; the others are cached by sibling modules using the same table/validator.
  • trimForSnippet collapses whitespace and hard-truncates at max-3 with '...'; large Exa/Jina markdown is capped (1200/1500/18000 depending on path) — snippet vs markdown caps differ, so the cached candidate snippet is much shorter than the fetched text.

Deep-Research Engine (deepResearch.ts)

A durable @convex-dev/workflow orchestrating a plan -> per-round [discover/rerank/read/assess] loop -> counter-evidence -> synthesize -> semantic claim-audit/revise -> persist artifact pipeline, modulated by agentKind (lite=2 rounds/gpt-5.4-mini, pro=4 rounds/gpt-5.5).

deepResearch.ts (~3193 lines) is the largest single module in the Aqsha agent subsystem. It implements an autonomous, source-grounded research engine as a durable Convex workflow. A run is kicked off only after a human approves a model-proposed plan: on the /deep-research turn the model calls the startDeepResearch tool (needsApproval) with a structured plan, and on approval the tool's execute calls startExecuteFromPlan, which starts deepResearchExecuteWorkflow (HITL flow with no hitlSessions involvement).

The workflow handler (deepResearch.ts:204) is intentionally thin: it normalizes the plan, then runs four big steps as durable workflow steps with retry — researchLoop (action, all discovery+reading+assessment), synthesize (action, report + chat summary), conditionally auditClaims (action, semantic verification + revision, skipped for "simple topics"), persistArtifact (mutation), and finalizeThread (mutation). All steps run with ACTION_RETRY = {maxAttempts:3, initialBackoffMs:2000, base:2}. The WorkflowManager (workflow.ts) caps maxParallelism at 6.

The engine is "modulated by the selected agent." Astra Lite runs the lite model (gpt-5.4-mini) everywhere with a tight 2-round cap; Astra Pro uses the heavy deep model (gpt-5.5) for planning/synthesis/revision with a 4-round cap. The internal helper models (query expansion, bucket planning, sufficiency assessment, counter-evidence decision, claim extraction, semantic verification) ALWAYS use DEEP_LITE_MODEL regardless of tier. Legacy/in-flight runs without agentKind default to "pro".

Lifecycle is tracked in three tables driven from this module: agentRuns (status queued->running->completed/failed/canceled, roundCount, sufficiencyStatus, verificationStatus, retryable, counts), agentRunSteps (11 fixed steps seeded at createRun), agentRunEvents (plan/query/search/read/gap/audit timeline), researchRoundStates, plus persisted researchSources, researchExtracts, citationChecks, and the artifacts/artifactVersions report. Billing is consumed up-front on retry/send via consumeCredits (flat DEEP_PRO_CREDITS=120 / DEEP_LITE_CREDITS=60).

  1. Start (HITL): startForMessage (or retry) creates an agentRuns row via createRun (status "queued", seeds 11 agentRunSteps) and schedules internal.agent.messages.generateDeepPlan (deepResearch.ts:465). That inline generation offers the startDeepResearch tool (needsApproval, hitlTools.ts:317).
  2. Approval -> workflow start: On user approval, the tool's execute (hitlTools.ts:330) calls startExecuteFromPlan (deepResearch.ts:480), which normalizes the plan and calls researchWorkflow.start(deepResearchExecuteWorkflow, {...}, {onComplete: handleWorkflowComplete, context:{runId, ownerUserId}}), then patches the run to status "running" with the workflowId.
  3. Workflow handler (deepResearch.ts:204): normalizePlan -> step.runAction(researchLoop) -> step.runAction(synthesize) -> if NOT simple topic step.runAction(auditClaims) -> step.runMutation(persistArtifact) -> step.runMutation(finalizeThread). Simple topic = plan.maxRounds === 1 && sufficiencyCriteria.length <= 2 (deepResearch.ts:222).
  4. researchLoop (deepResearch.ts:588): maxRounds = min(plan.maxRounds || roundCap, roundCap). Builds source buckets via planSourceBuckets (LLM, DEEP_LITE_MODEL, 4-6 buckets) with defaultSourceBuckets fallback. Then the per-round loop (for round=1..maxRounds): (a) ensureNotCanceled; (b) chooseRoundQueries (round 1 = bucket queries flat-mapped capped at 8; later rounds = LLM chooseExpansionQueries/chooseNextQuery); (c) records query event + researchRoundStates "planned"; (d) discoverCandidates fans out exa(limit 10)/jina(limit 8)/arxiv(limit 8) per query + crossref DOI lookup, dedupes to DISCOVERY_TARGET_PER_RUN=60, excludes unreliable+penalized domains; (e) mergeCandidatePool into a bounded pool (60); (f) selectCandidatesToValidate runs jinaRerank (topN min(14, n)) + diversifyCandidates, slices to 14; (g) validateAndRead reads each via readSourceWithFallbacks (Exa contents -> Jina reader), assesses quality, enforces PER_DOMAIN_ACCEPTED_CAP=2 and domainPenalties>=2 rejection, builds extracts (relevance high if rerankScore>0.6); accumulates into acceptedByKey/extractsByKey (extracts capped at MAX_EXTRACTS_PER_RUN=24); (h) assessSufficiency (LLM, DEEP_LITE_MODEL) returns insufficient/partial/sufficient + gapAssessment + assessEvidenceReadiness; (i) records gap event, updates loop progress, records researchRoundStates "completed". Loop breaks early if sufficiencyStatus==="sufficient" && readiness.ready.
  5. Counter-evidence (deepResearch.ts:873): shouldRunCounterEvidencePass (LLM, requires >=3 accepted sources) decides; if yes, one extra discovery+validate pass (selected.slice(0,4)) appends counter-evidence sources.
  6. If still not sufficient after all rounds -> sufficiencyStatus = "budget_exhausted". Final sources are numberSources (citationNumber 1..N, capped MAX_SOURCES_PER_RUN=14); extracts re-numbered to match. Returns {sources, extracts, roundState}.
  7. synthesize (deepResearch.ts:1004): generateText with deepModelForAgent(agentKind) + Output.object({markdown, chatSummary}). System prompt branches on assessEvidenceReadiness().ready (full report vs partial-artifact-with-limitations).
  8. auditClaims (deepResearch.ts:1065): sets verificationStatus "checking"; extractVerifiableClaims (<=16, DEEP_LITE_MODEL) then verifyClaimsSemantically (per-claim structural check + per-claim LLM classify supported/partially_supported/contradicted/unsupported, DEEP_LITE_MODEL). withEvidenceLimits appends an "## Evidence Limits" section. If shouldReviseUnsupportedClaims (any contradicted, or unsupported with confidence>=0.6) -> reviseUnsupportedMarkdown (deepModelForAgent) and verificationStatus "revised"; else passed/partial/failed.
  9. persistArtifact (deepResearch.ts:1154): persists extracts (researchExtracts), creates the report artifact (createResearchReportFromRun), persists researchSources (idempotent by sourceKey), persists citationChecks; patches run with activeArtifactId/counts. Short-circuits if run canceled.
  10. finalizeThread (deepResearch.ts:1252): saves assistant chat message (the chatSummary), attaches artifact to message, sets run status "completed" + retryable = (sufficiencyStatus==="budget_exhausted"||"partial"), schedules generateThreadTitle.
  11. onComplete handleWorkflowComplete (deepResearch.ts:1311): maps workflow result.kind canceled->markCanceled, failed->failRun (success path is a no-op since finalizeThread already completed the run).

Design decisions9›
Run the whole pipeline as a @convex-dev/workflow with 5 durable steps (researchLoop/synthesize/auditClaims/persistArtifact/finalizeThread), each action step wrapped in ACTION_RETRY.
Why Durable execution survives transient provider failures and gives idempotent, retryable checkpoints across a multi-minute multi-round research run; the workflow handler stays thin while heavy work lives in actions.
Modulate everything by agentKind: pro=4 rounds + gpt-5.5 for plan/synth/revise, lite=2 rounds + gpt-5.4-mini; but ALL internal helper LLM calls always use DEEP_LITE_MODEL.
Why Concentrates expensive model spend on user-visible planning/synthesis/revision while keeping the many internal control-loop calls cheap; flat per-tier credit pricing (120/60) maps cleanly to this.
HITL via the model-proposed startDeepResearch tool with needsApproval, not a hitlSessions FSM.
Why Uses @convex-dev/agent native in-thread approval; the workflow owns the run lifecycle end-to-end (matches the documented HITL unification direction).
Bound the candidate pool to 60 with bucket/origin-aware eviction and re-clamp plan.maxRounds via clampRoundCount on every entry point.
Why Prevents unbounded memory/cost growth across rounds and ensures a model that proposes maxRounds up to 8 can never exceed the tier cap.
Deterministic assessEvidenceReadiness gate separate from the LLM sufficiency assessment; both must agree (sufficient && ready) to early-stop.
Why Avoids an over-confident LLM declaring sufficiency prematurely; hard floors on readable sources/extracts/domains/buckets enforce a minimum evidence bar.
Two-stage claim verification (structural citation match + per-claim LLM classification) plus conditional revision and an always-appended Evidence Limits section.
Why Adversarially verifies claims against accepted extracts and makes weak/unsupported/contradicted claims visible or removes them, rather than overstating certainty.
Skip the audit step entirely for 'simple topics' (maxRounds===1 && sufficiencyCriteria<=2).
Why Avoids paying for semantic verification on trivial single-round runs where the overhead is unjustified.
handleWorkflowComplete explicitly maps result.kind 'failed' to failRun.
Why @convex-dev/workflow reports failures as kind 'failed' (no 'error' kind); without this a failed workflow silently fell through to success and was mis-marked completed (called out in an in-code comment).
Bound listEvents to RUN_EVENTS_DISPLAY_CAP=200 (newest-N then reverse).
Why listForThread fans events out across up to 20 runs in one reactive query; the perf commit caps pathological multi-round runs to keep the progress panel query bounded.
Gotchas & sharp edges10›
  • startDeepResearch tool allows maxRounds up to 8, but normalizePlan->clampRoundCount silently re-clamps to roundCapForAgent (4 pro / 2 lite). The model's proposed value above the cap is never honored — and the user approves a number that may be reduced.
  • All internal control-loop LLM calls (bucket planning, query expansion, sufficiency, counter-evidence decision, claim extraction, AND every semantic claim verification) hardcode DEEP_LITE_MODEL regardless of agentKind — only the plan/synthesis/revision use the pro model. Pro runs are not fully 'pro'.
  • Billing is a FLAT up-front estimate (120/60 credits) based only on prompt token count for plan estimation, decoupled from actual provider/LLM spend; long multi-round runs cost the same as short ones.
  • planResearch (deepResearch.ts:523) is a full standalone plan-generation action that the live HITL path does NOT use — the live plan comes from the model's startDeepResearch tool input; planResearch is effectively a parallel/legacy path that still writes budgetJson and a plan event.
  • handleWorkflowComplete success path is a no-op: finalizeThread already sets status 'completed'. The onComplete only matters for canceled/failed; an in-code comment warns that without the 'failed' branch a failed workflow was mis-marked completed.
  • Early-stop requires BOTH the LLM sufficiencyStatus==='sufficient' AND the deterministic readiness.ready (>=10 readable sources, >=8 extracts, >=4 domains, >=3 buckets). The readiness floors are high (10 readable sources), so many runs hit budget_exhausted and only ever produce a 'partial' artifact, marking the run retryable.
  • extractsByKey is keyed by sourceKey + first 80 chars of quote and capped at 24; once full, the loop breaks out of accepting further extracts in that round (deepResearch.ts:751), potentially discarding otherwise-accepted sources' extracts mid-round.
  • ensureNotCanceled is only checked at the top of each round and at the start of synthesize/auditClaims — cancellation during a long discovery/read fan-out is not interrupted until the next checkpoint.
  • DOI/crossref discovery is best-effort (limited to 4 DOIs, .catch->[]); arXiv-origin sources are treated as readable in readiness even without a successful read (origin==='arxiv' counts as readable).
  • verifyClaimsSemantically does a per-claim LLM call in a sequential for-loop (no batching), so audit latency/cost scales linearly with up to 16 claims.

Threads, thread titles, run lifecycle, and rate limiting

App-side thread CRUD/listing over the @convex-dev/agent thread store via a threadMetadata sidecar, prompt-derived + LLM-refined auto titles, an agentRuns status machine driven by runLifecycle helpers, and a @convex-dev/rate-limiter that gates message sends (sendMessage / globalSendMessage / globalTokenUsage).

This component is the thread-and-run control plane for the Aqsha agent subsystem. The @convex-dev/agent component owns the canonical thread record (id, userId, title) and the message store; this code layers an app-owned threadMetadata sidecar table on top to track product-level state the component does not model: filed-under workspaceId, lastActivityAt, lastMessagePreview, messageCount, a thread status ("idle" | "streaming" | "failed"), and the sticky composer lastAgentKind. Thread reads always join the component thread (source of truth for title and ownership) with this sidecar (summarizeThread in threads.ts:45). Titles live on the component thread and are patched through astra.updateThreadMetadata (the Agent instance bound to components.agent), not in the sidecar.

Auto titling happens in two layers. On send, a prompt-derived title is computed synchronously (threadTitleFromPrompt, threadTitles.ts:11) — strip mention markers, collapse whitespace, hard-cap 80 chars with word-boundary ellipsis — and applied only if the current title is empty or the placeholder "Thread baru" (shouldUsePromptTitle, threadTitles.ts:23). After a reply finishes, an LLM refines it: generateThreadTitle (messages.ts:1274) calls generateObject on the lite chat model and overwrites the title if still default/fallback, after normalization (normalizeGeneratedThreadTitle) and a quality gate (isUsableGeneratedThreadTitle, threadTitles.ts:36) that rejects "Thread baru", a blocklist of meta-titles, and anything starting "request for ".

agentRuns is the run-status machine. Inline chat runs are created by startInlineRun directly in status: "running" (no queued state for inline) and resolved by completeInlineRun (→ completed, or → waiting when a native HITL pause is pending) or failInlineRun (→ failed). Deep-research runs use the same table but flow through the @convex-dev/workflow workpool defined in workflow.ts, transitioning running → (per-step markStep) → completed/failed/canceled. runLifecycle.ts provides the cross-cutting helpers: hasActiveReplyRun gates a second concurrent send (returns reply_in_progress), hasOtherActiveReplyRun prevents a stale terminal handler from clobbering a newer run's thread status, and markThreadStatusAfterTerminalRun flips the sidecar status only when the thread is still "streaming" and no newer active run exists.

Rate limiting is centralized in limits.ts (the RateLimiter from @convex-dev/rate-limiter wired to components.rateLimiter). For sends, three limits are checked-then-consumed inside checkAndConsumeSendQuota (messages.ts:240): a per-user sendMessage fixed window, a global globalSendMessage token bucket, and a global globalTokenUsage token bucket sized by estimated input tokens. rateLimits.ts only exposes a read-only getSendStatus query so the composer can show a retry countdown; the actual gate (consume) lives in messages.ts. Plan-based monthly credits (consumeCredits) are the real per-user quota and run before the rate-limit gate.

Design decisions7›
Split thread state into the @convex-dev/agent component thread (title, userId, messages) and an app-owned threadMetadata sidecar (workspaceId, status, preview, counts, lastAgentKind).
Why The component does not model product concerns like filed-under workspace, streaming/failed status, last-activity ordering, or the sticky composer agent tier; the sidecar adds them without forking the component. Title stays on the component (patched via astra.updateThreadMetadata) so it remains the single source for thread.title.
Lazily create the sidecar row: only workspaced threads get a threadMetadata row at creation; others are upserted on first send.
Why Avoids empty sidecar rows for never-used threads; summarizeThread tolerates the missing row with defaults. Tradeoff: a freshly created non-workspaced thread shows defaults until first send.
Two-stage titling: instant prompt-derived title on send, then async LLM refinement after the first reply, each guarded to only overwrite a still-default title.
Why Gives an immediate human-readable title with zero latency/cost, then upgrades it to capture real intent; guards (shouldUsePromptTitle / generateThreadTitle's title-still-default check) prevent clobbering a user- or LLM-set title.
Inline runs start directly in 'running' (skipping 'queued'); 'queued' exists in the schema for deep/legacy rows.
Why Inline generation is scheduled immediately (runAfter 0) so there is no meaningful queue wait; the broader status union still supports workflow/deep runs and the 'waiting' HITL pause.
Terminal handlers (markThreadIdle/markThreadFailed/markThreadStatusAfterTerminalRun) early-return when a newer active run exists or the sidecar isn't 'streaming'.
Why Multiple runs can overlap on one thread (e.g., resume after HITL); without the guard a slow older run's completion would incorrectly mark the thread idle/failed over a newer in-flight run.
Run plan-based credit consumption BEFORE the @convex-dev/rate-limiter check, and keep the rate limiter as a throughput safety valve only.
Why Monthly plan credits are the real per-user quota; the rate limits (esp. globalTokenUsage/globalSendMessage) exist to protect the system/provider against spikes, explicitly 'never enforced per user' for the global token bucket.
rateLimits.ts only exposes a read-only getSendStatus query; the consume happens in messages.ts.
Why The composer needs a non-mutating way to show a retry countdown without consuming a token; check() is side-effect-free, while the actual limit() consume is co-located with the send mutation.
Gotchas & sharp edges10›
  • threadMetadata is NOT created for non-workspaced threads at creation time — only on first send (upsertThreadMetadata). Until then summarizeThread returns defaults (status 'idle', messageCount 0, empty preview), so a brand-new empty thread looks identical to an idle one.
  • There are TWO independent status enums: agentRuns.status (queued|running|waiting|completed|failed|canceled) and threadMetadata.status (idle|streaming|failed). They are kept in sync only by the terminal handlers; a run going to 'waiting' (HITL) leaves the thread sidecar at 'streaming' (markThreadIdle is skipped when deepStarted/pending).
  • Thread title lives on the component thread, NOT in the threadMetadata sidecar. There is no plain rename mutation in threads.ts; renames only happen implicitly via prompt-derived title (send) and the LLM generateThreadTitle, both gated to only overwrite a still-default title.
  • hasActiveReplyRun only counts queued|running as active — a run in 'waiting' (paused on HITL) is NOT considered active, so a new send is allowed while a HITL pause is outstanding.
  • Active-run guards scan only the newest 8 runs (take(8)); if a thread accrued >8 newer runs, an older active run could be missed — unlikely but a hard cap.
  • Inline run failure sets retryable:false and errorCode 'normal_reply_failed'; deep-research failRun sets retryable:true. Retry UX therefore differs by run type.
  • threads.remove loops deleteAllForThreadIdAsync up to 50 times synchronously in one mutation; very large threads may hit the cap and throw thread_delete_in_progress, requiring the user to retry.
  • 'Thread baru' is a magic-string sentinel checked in multiple places (threads.ts default, shouldUsePromptTitle, generateThreadTitle gate, isUsableGeneratedThreadTitle). Changing the default title string would silently break all the 'still needs a title' guards.
  • globalTokenUsage is check()'d with the estimated token count in checkAndConsumeSendQuota but only sendMessage+globalSendMessage are limit()'d there; the actual globalTokenUsage consume happens later (messages.ts:1740), so the upfront check is advisory.
  • listByWorkspace paginates the sidecar then refetches each component thread and filters foreign/missing ones, so a page can return fewer than paginationOpts.numItems entries (post-filter shrinkage).

This component is the entire user-facing chat surface that drives the Convex/@convex-dev/agent backend. The Composer (composer.tsx) collects prompt text, slash-command tokens, @mention workspace/paper context pills, file attachments, and a lite/pro agent selection, then turns them into a single backend call. Critically, the composer only schedules generation: send/startThread return immediately (returning a SendResult union), and the reply is streamed back reactively rather than awaited.

Streaming render is handled by ChatThreadState (chat-thread-state.tsx) via useUIMessages(api.agent.messages.list, ..., { initialNumItems: 30, stream: true }) from @convex-dev/agent/react. Messages are sorted and interleaved with deep-research runs, then each row is rendered by MessageRow (message-row.tsx) which assembles text from parts (text deltas) and shows a "Sedang menulis..." activity indicator while status === "streaming".

Human-in-the-loop is fully native in-thread: there is no separate FSM. Pending HITL is derived purely from the message stream — hasPendingHitl (hitl-parts.ts) scans assistant message parts for tool parts in state approval-requested (approval tools) or input-available (askUser). When pending, the composer is blocked (hitlBlocking) and MessageHitlParts renders the appropriate card (Question / Confirm / Review-Plan). The user's answer/approval is recorded by useHitlResume mutations, and once the derived hasPending flips to false, resumeHitl fires to resume generation.

The TanStack-Query/Convex-query state pattern is centralized in lib/convex-query.ts: thin generic wrappers over @convex-dev/react-query (useConvexQueryData for reactive reads, useConvexMutationFn/useConvexActionFn for fire-and-forget calls, useConvexOptimisticMutationState for the optimistic user-message insert). The composer's lite/pro selection is orthogonal to the deep path — Deep Research is triggered only by a resolved commandId (/deep-research), and the backend derives the deep execution kind from that commandId, not from agentKind.

Design decisions8›
Send schedules generation and returns immediately; the reply streams back via a reactive query (useUIMessages), not via the mutation's return value.
Why Decouples the request from the long-running agent run. The composer must therefore also lock on isGenerating (threadStatus.status==='streaming'), because isSending alone re-opens the composer before streaming finishes (comment at chat-thread-state.tsx:104-106).
HITL is native in-thread, derived entirely from the message stream — no separate hitlSessions/hitlCards FSM.
Why A pending tool part (askUser input-available, or any approval-requested tool) blocks the composer and renders a card; resolving every pending tool on a step resumes generation. Matches the @convex-dev/agent component reference UI (use-hitl-resume.ts:21-25). Aligns with the recorded HITL-unification direction in memory.
resumeHitl fires only after the derived hasPending flips to false, tracked via pendingResumeRef + lastMessageIdRef.
Why The record mutations only persist a decision and return a messageId; firing resume per-decision would auto-deny sibling tool calls. Waiting for hasPending=false lets the user answer/approve all pending tools on a step first (use-hitl-resume.ts:78-85).
agentKind (lite/pro) is orthogonal to the deep-research path; deep is driven solely by commandId.
Why Lets either tier run a deep workflow ('Lite-deep' or 'Pro-deep'); the backend derives execution kind from commandId via promptExecutionKindForCommand, keeping the model/tier choice independent (composer-model.ts:102-104, agent/messages.ts:605).
Optimistic user-message insert via withOptimisticUpdate + insertAtTop into the messages.list paginated cache.
Why Gives an instant echo of the user's bubble (with command chip + context artifacts) before the server round-trip; only api.agent.messages.send uses the optimistic variant (startThread does not, since it navigates to a fresh thread).
Mention pills are sent as rich (marked) content (richContent) while plain content is the fallback.
Why Lets the user bubble re-render @mention pills inline at their typed positions (message-row.tsx parseMentionSegments), while context refs are also sent structurally as selectedContextArtifactIds/WorkspaceIds + snapshot for backend RAG filtering (add semantics).
All frontend Convex access goes through lib/convex-query.ts TanStack wrappers (per CLAUDE.md), not raw convex/react hooks.
Why useConvexQueryData for reactive reads ('skip' for gating), useConvexMutationFn/ActionFn for fire-and-forget, useConvexOptimisticMutationState for optimistic writes; centralizes pending/error/loading as TanStack server-state.
useUIMessages is imported directly from @convex-dev/agent/react (not wrapped in the TanStack adapter).
Why The agent component's streaming hook has no TanStack-adapter equivalent; CLAUDE.md explicitly permits direct convex/react-family imports for utilities without an adapter. It coexists with TanStack queries for runs/artifacts/sources.
Gotchas & sharp edges10›
  • The composer must lock on BOTH isSending (local) and isGenerating (threadStatus.status==='streaming'); send returns immediately so isSending alone would re-open the composer before the agent finishes streaming (chat-thread-state.tsx:104-106).
  • HITL pause/resume is implicit: nothing 'pauses' explicitly — hitlBlocking is purely derived from message parts, and resumeHitl only fires after hasPending flips false. If a tool part's state strings ever diverge from 'approval-requested'/'input-available', the composer would silently stay blocked or never resume.
  • resumeHitl uses refs (pendingResumeRef/lastMessageIdRef) outside React state; if the component unmounts/remounts (e.g. panel toggle) between recording a decision and hasPending flipping, the pending resume can be lost.
  • agentKind is forced to 'lite' for free users at the hook level (composer-agent-selector.tsx:53), so even a stale 'pro' selection in state is coerced before submission — but the SELECTED state can still be 'pro' if canUsePro flips.
  • Deep Research is NOT selected via the Lite/Pro dropdown; it is only triggered by the /deep-research command (commandId) — discovery surfaces hardcode agentKind:'pro' + commandId:'deep-research' (use-start-research.ts:31-33).
  • richContent (mention-marked) vs plain content divergence: the bubble renders richContent when present, but if richContent is empty (e.g. attachments-only synthetic text), it falls back to submission.content — two different code paths feeding the same message.
  • Attachments are uploaded BEFORE the send mutation; an upload failure throws and aborts the whole submit (content already cleared, then restored only in the !result.ok branch, NOT in the catch — the catch re-throws after setIsSending(false), so on upload error the cleared text may be lost since clearing happens after upload).
  • Actually content is cleared at composer.tsx:314 only AFTER uploads succeed, so an upload throw (before clearing) preserves text — but a post-clear backend error relies on restoreComposerContentAfterBlockedSend; the generic catch path (network/throw) does NOT restore content.
  • startThread does not get an optimistic update (only send does), so the very first message of a new thread has no instant echo until navigation + stream subscription.
  • useUIMessages is the only piece bypassing the mandated TanStack adapter (per CLAUDE.md it's allowed since no adapter equivalent exists), so its loading/error semantics differ from the rest of the screen's TanStack-managed state.
