# Waitlist Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Membangun waitlist custom Aqsha dengan verifikasi email Resend, mengganti seluruh CTA auth di marketing site, dan menonaktifkan akses product melalui `WAITLIST_MODE`.

**Architecture:** `apps/www` menjadi public UI static untuk `/waitlist`, `apps/api` menyediakan public REST endpoints, `packages/db` menyimpan `waitlist_entries`, dan `packages/services` memiliki domain logic serta client Resend. `apps/web` hanya mengontrol redirect auth/product ketika mode waitlist aktif.

**Tech Stack:** Astro 5 + React 19, Elysia, Drizzle/PostgreSQL, Redis + `rate-limiter-flexible`, Resend HTTP API via `fetch`, Clerk middleware, Bun 1.3.10.

## Global Constraints

- Gunakan Bun `1.3.10`; jalankan `bun install`, bukan `npm`, `pnpm`, atau `yarn`.
- Canonical marketing site adalah `apps/www`; jangan mengubah `apps/web/features/marketing` karena frozen.
- Field waitlist hanya `email` wajib dan `companyOrUniversity` opsional; tidak ada nama.
- Verifikasi email wajib; token disimpan sebagai hash, single-use, dan berlaku 24 jam.
- Data waitlist hanya digunakan untuk notifikasi peluncuran, bukan newsletter marketing.
- API mengembalikan structured application errors `{ message, code, severity?, field? }`.
- Duplicate email tidak boleh diekspos melalui response yang berbeda.
- Tidak ada admin UI atau export CSV pada MVP.
- Gunakan rate limit Redis untuk submit, resend, dan verification abuse.
- Semua CTA marketing mengarah ke `/waitlist`, bukan `appUrl('/sign-in')` atau `appUrl('/sign-up')`.
- `WAITLIST_MODE=true` harus dapat mengarahkan auth/product ke `${NEXT_PUBLIC_SITE_URL}/waitlist` tanpa menghapus flow auth lama.
- Setiap task berakhir dengan test yang relevan dan commit terpisah.

- [ ] **Step 5: Implement `WaitlistService.join`.**

Algorithm:

1. Normalize and validate input.
2. Find by normalized email.
3. If the row is `confirmed`, return `{ ok: true, action: "already_confirmed" }` without sending mail.
4. Create a random token, hash it, and compute `expiresAt`.
5. Insert a new `pending` row or update verification fields on an existing `pending` row.
6. Build `${siteUrl.replace(/\\/$/, "")}/waitlist/verify?token=${encodeURIComponent(token)}`.
7. Send mail through injected `sendEmail`.
8. If sending fails, leave the row `pending` so a later submit can retry; propagate the structured email error.
9. Return `{ ok: true, action: "verification_sent" }`.

If an insert loses a unique-email race, re-read the row and follow the same existing-row behavior instead of surfacing a database error.

- [ ] **Step 6: Implement `WaitlistService.verify`.**

Hash the supplied token, find a pending row by hash, reject missing or expired rows with `waitlist_token_invalid` status 400, and call `WaitlistRepo.confirmPending`. If the conditional update returns false, reject with the same safe error. Successful verification returns `{ ok: true }`.

- [ ] **Step 7: Add service integration tests with a fake email sender.**

Use a real DB when `DATABASE_URL` exists and a fake sender that records `{ to, verificationUrl, expiresAt }`. Test:

- new pending row and one email sent;
- existing pending row gets a replacement token and one email sent;
- existing confirmed row sends no email;
- valid token confirms and cannot be reused;
- expired and invalid tokens return `waitlist_token_invalid`;
- sender failure leaves the row pending;
- raw token is not equal to the persisted hash.

export function isWaitlistMode(): boolean {
